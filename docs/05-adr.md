# 05. Architecture Decision Records

*Имена каталогов с 2026-11-25 — римские: `outbox` → `acta`, `ledger` → `fasti`, `artifacts` →
`tabularium`, `profile` → `persona`, `state` → `cella`, `tasks` → `mandata`, коробка → `castrum`.
Решения в ADR от этого не менялись — менялись имена объектов, на которые они ссылаются.*

Решения записаны так, чтобы их не пересматривать без причины. Статус: `принято` (2026-11-24),
`предложено` (ждёт решения владельца), `архив` (устарело, оставлено для истории).

---

## ADR-001. Augustus — отдельный экземпляр Hermes-agent на каждую коробку

**Принято.** Оркестратор проекта — не новый код и не личная ассистентка, а второй экземпляр
`nousresearch/hermes-agent` (MIT) со своим томом, профилем, ключами и бюджетом. Одна коробка = один проект.

**Почему.** Писать заново агентский цикл, планирование и память — месяцы ради того, что уже есть и
обновляется другими. Личный Hermes при этом остаётся снаружи: смешивать «контекст моей работы» и
«контекст проекта» — верный способ испортить оба.

**Следствие.** Пантеон зависит от стороннего runtime: его API инструментов и формат данных могут
измениться. Лечится фиксацией версии (ADR-010) и тем, что данные проекта и записи работы лежат вне
runtime.

## ADR-002. Коробка живёт рядом с проектом, проект монтируется

**Принято.** `~/pantheon/castra/<project>` с compose-файлом и томами; репозиторий монтируется внутрь,
а не копируется. «Настоящая коробка» (контейнер, в который проект кладут) — отдельная будущая работа.

**Почему.** Проект остаётся чистым: его git не содержит инфраструктуру запуска. Коробка переносится
одним каталогом. Обратная зависимость не возникает: удалили коробку — проект цел.

**Следствие.** Два места вместо одного; связь между ними — путь в `castrum.toml`. При переносе на другую
машину путь может потребовать правки — это единственное место.

---

## ADR-003. Правда о проекте — в репозитории, записи работы — в коробке

**Принято.** Требования, политика, архитектурная модель и ADR — файлы в репозитории, ревьюятся как
код. Задачи, контракты, попытки, прогоны, события — в коробке.

**Почему.** Обещания проекта должны пережить любую коробку и ревьюиться вместе с кодом; история работы
принадлежит конкретной коробке. Один владелец на факт — иначе проверка и память разойдутся.

**Следствие.** Клон репозитория без коробки — проект без истории; коробка без проекта — история без
объекта. Оба состояния допустимы и видимы.

---

## ADR-004. Caesar — единственный инструмент записи, который получает Augustus

**Принято (требует проверки на практике).** Профиль Августа не имеет родного shell, редактора и записи
файлов; запись идёт только через `pantheon run`, то есть через контракт Caesar.

**Почему.** Полномочия, которые держатся текстом в промпте, не держатся вовсе. Если у Августа есть
родной shell, Caesar становится формальностью, а концепция «исполнение под контролем» — декларацией.

**Следствие.** Августу запрещено то, что он мог бы сделать иначе. Чтение (проверки, архитектура)
разрешено напрямую — ограничение только на запись и запуск исполнителей.

## ADR-005. Trajan — это trajan, вердикт считает код

**Принято.** Контур проверки не переписывается: используется trajan как есть, через контракт
«изменение + требования + политика → отчёт». Вердикт остаётся функцией кода; модель может добавлять
находки, но не может изменить вердикт.

**Почему.** Это единственная часть экосистемы с доказанной работоспособностью: 690 тестов, 25 кейсов,
живые прогоны, повторяемость 48 из 48. Написать второй контур — потерять доказательства.

**Следствие.** Trajan наследует ограничения trajan: Python-centric проверки, политика в TOML,
ревьюер через OpenAI-совместимый клиент. Расширение — через политику и плагины, а не форком.

---

## ADR-006. Aurelius: TOML-модель в репозитории, проверка — детерминированная

**Принято.** Архитектурная модель — файл в репозитории (модули, разрешённые зависимости, слои,
инварианты, `baseline`/`target`). Проверка — детерминированная, поверх существующих инструментов
(import-linter, tach, dependency-cruiser), а не свой анализатор. LLM предлагает черновик модели, человек
принимает.

**Почему.** «Ответственность компонента» и «удачный интерфейс» не проверяются машиной; проверяемо то, что
сводится к правилу. Свой анализатор — изобретение велосипеда, запрещённое концепцией.

**Следствие.** Aurelius отвечает на «какие ограничения применимы и нарушены ли они», но вердикт
выпускает Trajan.

---

## ADR-007. Маршрутизация — таблица по объявленным полям задачи

**Принято.** Задача объявляет объём: пути и тип (docs / bugfix / feature / architecture / security).
Таблица «объём → контуры» детерминирована. LLM может предложить изменить план, но план — данные.

**Почему.** LLM-классификатор ошибается тихо: пропущенная архитектурная проверка обнаруживается через
недели. Явное поле видно в задаче и оспаривается человеком.

**Следствие.** Задача без объявленного объёма не стартует — это дешевле, чем угадывать.

---

## ADR-008. Никакого RPC, шины и сервисов в MVP

**Принято.** Файлы, CLI, коды возврата, json. Один контейнер на коробку (Август). Локального API нет.

**Почему.** «Позже понадобится» — главный источник переусложнения; второй пользователь и параллельные
исполнители появятся не раньше, чем заработает первый сценарий.

**Следствие.** Координация «онлайн» невозможна; для одного инженера она и не нужна.

---

## ADR-009. Глубина проверки — таблица риска, которая расширяется, но не сужается молча

**Принято.** Сопоставление «пути/тип изменения → минимальный набор проверок» живёт в политике.
История находок может **добавить** проверку; убрать — только человек и только записью.

**Почему.** Динамическое планирование проверок — правильная идея с плохой реализацией по умолчанию: если
её определяет модель, глубина становится настроением. Минимальный пол — данные.

**Следствие.** Trajan всегда может проверить больше, чем минимум, но не меньше без явного решения.

---

## ADR-010. Образ Hermes фиксируется по тегу в каждой коробке

**Принято.** `castrum.toml` хранит точный тег; `latest` запрещён.

**Почему.** Обновление «одной командой» снесло бы все коробки разом, а воспроизводимость — требование,
которое мы собираемся доказывать.

**Следствие.** Обновление — осознанная операция на коробку, с записью в реестр.

---

## ADR-011. Поток наружу односторонний

**Принято.** Коробка пишет сводку в `acta/`; личный Hermes читает. Обратной зависимости нет.

**Почему.** Ассистент не должен быть обязательным для работы над проектом, иначе его падение — это
падение разработки, а его контекст — утечка между проектами.

**Следствие.** Личный Hermes может отставать от коробки; это нормально и видно по сводкам.

---

## ADR-012. Полезность Пантеона доказывается заранее записанным ожиданием

**Принято.** До прогона фиксируются задачи и ожидаемый результат (вердикт, находки, ограничения); после
прогона сравнивается. Протокол — в [09-evaluation.md](09-evaluation.md).

**Почему.** Это единственный способ отличить «система полезна» от «система запускается»; в trajan этот
принцип дал 0 из 4 ложных тревог вместо уверенного «работает».

**Следствие.** Демонстрации «смотрите, всё зелёное» не считаются результатом.

---

## ADR-013. Архитектор — советник в отдельной сессии того же агента, а не второй экземпляр

**Принято 2026-11-24, к реализации.** Архитектурная роль — вторая сессия того же агента в коробке:
проект только на чтение (включая историю git), свои инструкции и инструменты. Она не пишет код и
тесты и не пушит; её продукт — документы (бриф, аудит, ADR, план), архитектурная модель и требования,
и в проект они попадают только через ворота, как любое изменение. Утверждение рамки — запись среды с
отпечатком модели, а не поле в файле, который эта роль может переписать; задача, построенная против
неутверждённой рамки, не может закрыться тихо.

**Почему.** Два экземпляра дают две памяти, два ключа и два состояния, а граница, которая защищает, —
права записи и контракт выхода, а не число процессов. Отдельная сессия при этом сохраняет главное:
разговор только об архитектуре, операционная память в него не течёт.

**Следствие.** Архитектурные изменения проходят тот же путь «задача → ворота → проверки → запись →
утверждение», что и код; различается вид задачи и политика путей.

## ADR-014. Вид задачи ограничивает пути в воротах

**Принято 2026-11-24, к реализации.** У вида задачи есть таблица разрешённых путей, и задача может
объявить только подмножество: код не может трогать `.pantheon/`, архитектура не может трогать `src/`
и `tests/`. Отказ — с причиной и записью, как любой другой отказ ворот.

**Почему.** Сейчас разрешённые пути берутся из самой задачи, поэтому любая задача может объявить себе
архитектурную модель, и граница ролей держалась бы на честном слове.

**Следствие.** Таблица видов живёт в репозитории проекта и ревьюится как код; новая роль — строка в
таблице, а не новый код ворот.

## ADR-015. Коммит — после проверки, и это единственное, что ворота оставляют в git

**Принято 2026-11-24, к реализации.** Изменение применяется, проверяется, и только потом коммитится —
с вердиктом и ссылкой на отчёт в сообщении. В коммит входят только пути этой задачи, автор служебный,
пуш — только по просьбе владельца. Неудачный вердикт — тоже коммит с пометкой, а не тишина.

**Почему.** История становится доказательством, а не списком правок; после задачи дерево чистое, есть
точка отката. Отпечаток повтора считается по содержимому файлов, поэтому коммиты повтор не ломают.

**Следствие.** Вердикт каждой задачи виден в git; спрятать неудачу нельзя.

---

## ADR-016. Кампания связывает рамку с работой

**Принято 2026-11-24, к реализации.** Кампания — обещание «проект должен стать таким»: бриф, отпечаток
рамки, критерий приёмки, бюджет и упорядоченные шаги с зависимостями. Шаг объявляет намерение и
приёмку, а не дифф. Шаги Август пишет сам по утверждённой архитектуре, архитектор проверяет
соответствие рамке. Вердикт кампании считает код: все шаги решены, архитектурная проверка проходит,
критерий приёмки выполнен, бюджет не превышен — иначе кампания не закрыта. У плана есть ревизии:
механические изменения (разбить шаг, переставить независимые, сузить пути, уточнить бюджет шага)
Август делает сам с записью причины; смысловые (приёмка шага, состав шагов, замысел, отпечаток
рамки, бюджет кампании) — только с владельцем.

**Почему.** Без кампании двадцать правильных диффов дают архитектуру, которой никто не хотел:
каждая задача проверяется отдельно, а согласованность между ними никто не держит. Жёсткий план,
который останавливается на любом отклонении, упирается в реальность на первом же шаге.

**Следствие.** Итоговый вердикт ссылается на ревизию плана, которая исполнялась; «делали не то» — это
diff между ревизиями, а не воспоминание.

## ADR-017. Бриф — обещание, аудит — доказательство

**Принято 2026-11-24, к реализации.** Бриф (цели, не-цели, ограничения, критерии успеха, открытые
вопросы) живёт в репозитории: это обещание о проекте, оно должно пережить коробку. Аудит (что за
проект, из чего состоит, где нарушены границы, где документация разошлась с кодом) живёт в коробке:
это доказательство про конкретное дерево на конкретную дату, в репозитории он стал бы стареющей
документацией. Выводы аудита попадают в бриф или архитектуру только через владельца.

**Почему.** Утверждение и дата — разные вещи. Обещание утверждает человек и оно действует, пока его не
заменили; доказательство не утверждают, у него есть дата и отпечаток, и оно стареет.

**Следствие.** Проект без коробки теряет аудит, но не теряет бриф и рамку; пропущенная фаза
записывается как пробел, а не замалчивается.

## ADR-018. Режим кампании — два способа закрыть шаг, одно правило коммита

**Принято 2026-11-24, к реализации по частям.** У кампании есть поле `mode`: `manual` (каждый шаг
после вердикта ждёт владельца) и `auto` (шаги закрываются сами). Правило коммита при этом одно:
локальный коммит только после вердикта `pass` или `pass_with_conditions`, с вердиктом и отчётом в
сообщении, только путями задачи, автор — служебный, пуш — вручную. Разница между режимами не в
проверке, а в том, кто говорит «дальше». Предохранители авто режима — часть объекта кампании с
самого начала, даже пока исполнителя нет: бюджет кампании и потолок шага, число попыток, детектор
зацикливания, замороженный план (механические правки можно, смысловые — нет), запрет пуша и запрет
осмысленных изменений рамки. Незнакомый или необъявленный режим останавливает работу, а не
становится молча ручным.

**Почему.** Автономность соблазнительно сделать вторым, более коротким путём: «если никто не смотрит,
коммитим без проверки». Тогда ручной и авто режимы перестают быть одним контуром, и появляется код,
который никто не проверял, — ровно то, от чего весь проект защищается. Режим, который объявлен но не
умеет работать, тоже опасен: он выглядит как работающая автономность. Поэтому `auto` честно
отказывает, пока нет исполнителя: пробел виден, а не замалчивается.

**Следствие.** Шаг 2 порядка работ (коммит после проверки) — это уже первый кусок авто цикла: решение
«коммитить» считает код из вердикта и режима, а не вызывающая сторона. Прикрутить исполнителя позже
будет добавлением, а не переделкой.

**Обновление 2026-11-24.** Исполнитель появился (ADR-022): `auto` исполняет `pantheon advance`; правило
коммита и предохранители остались теми же, поэтому отказ «пока нет раннера» снят.

## ADR-019. Повтор — только по причине из вердикта и только если изменение изменилось

**Принято 2026-11-24, к реализации вместе с кампанией.** В авто режиме повтор после не-`pass` вердикта
разрешён, когда причина названа вердиктом и лежит внутри путей задачи (находка в коде, которую можно
исправить), и когда новое изменение отличается от предыдущей попытки. Число повторов ограничено
попытками и бюджетом шага. Технический сбой чтения (читатель не ответил, стоимость не названа) даёт
одну повторную попытку, вторая — стоп. Стоп сразу, без повторов: находка требует менять набор
разрешённых путей, вид, рамку, приёмку или состав шагов; тот же отпечаток изменения или те же находки;
исчерпан бюджет; нет читателя.

**Почему.** Повтор — это прогресс, только если изменилось то, на что указывала проверка. Иначе это та
же попытка, оплаченная второй раз, и модель, которая «пробует ещё», вместо кода, который сказал
«нельзя». Повтор, запущенный кодом по названной причине, и повтор, запущенный моделью по настроению, —
разные вещи, и различить их задним числом невозможно.

**Следствие.** Человек получает не «не получилось», а «три попытки, находка повторилась дважды,
остановился». Не смог — это записанный стоп с причиной, а не тишина.

## ADR-020. Контекст собирает код: дайджест записей и пакет под задачу

**Принято 2026-11-24.** Память проекта — это записи коробки: контракт задачи, попытка ворот, отчёт
проверки, коммит. Модели нужен не весь архив, а ответ «что уже происходило вокруг этих путей». Его
пишет код: дайджест `tabularium/commentarii/digest.json` — одна строка на законченную задачу (цель, вид,
вердикт, тронутые пути, адрес полной записи), детерминированный и ограниченный, с названными краями
(сколько записей не влезло, что не читается). Перед вызовом модели код собирает пакет
`tabularium/<task>/fascis-<at>.json`: утверждённая рамка с отпечатком, записи, чьи пути попали в
объявленный объём (с причиной отбора), указатели на полные записи, потолок размера и строка
`left out` обо всём, что не вошло. Пакет уходит в `request.json`, в запись диспетча, в acta и
печатается при `--json`; модель видит его до первого токена.

**Почему.** Если модель ищет контекст сама, цена поиска не видна, а «что она читала» непроверяемо.
Если контекст кладут в промпт руками, он дрейфует от записей и от рамки. Код собирает его из тех же
файлов, по которым считает вердикт: отбор можно пересчитать, а запись прогона говорит, что именно
знала модель. Указатель вместо копии — не экономия ради экономии: полная запись остаётся
единственным источником, а пакет — оглавлением к ней.

**Следствие.** Пакет больше промпта без контекста: это осознанная плата за то, что модель знает
историю. Экономию должна показать кампания (те же вердикты, меньше вызовов и токенов), поэтому журнал
прочитанного и бюджет чтения остаются следующим шагом, а не выдуманным числом сейчас.

## ADR-021. Повтор — это решение кода, а не второй запуск

**Принято 2026-11-24.** У кампании есть `mode` и `attempts`; повтор шага идёт только через
`pantheon step --retry`, и разрешает его код, а не человек и не модель. Решение строится так: шаг
закрыт — повторять нечего; записанная остановка не пересматривается; исчерпанные попытки и
потраченный бюджет кампании — стоп; вердикта нет (ворота отказали) — стоп, второй такой же отказ
ничего не даст; находка с местом вне объявленных путей — стоп, менять надо план или рамку; находка
внутри путей или провалившаяся проверка объявленного изменения — повтор разрешён. Перед повтором
черновик провалившейся попытки откатывается её собственным диффом, чтобы повтор начинался от
принятого дерева и коммит оставался «HEAD + изменение». Если модель ответила тем же диффом, он не
применяется второй раз: отпечаток в координатах проекта совпадает, шаг записывает остановку.

**Почему.** Повтор — единственное место, где автономность может незаметно превратиться в оплаченный
цикл: та же ошибка, та же модель, та же цена. Разрешение «ещё раз» звучит как действие, но это
решение, и принимать его должен код по названной причине, а не тот, кто устал смотреть. Откат
черновика — не уборка, а условие честности: коммит обещает «вердикт относится к этому изменению на
этом дереве», и дерево не должно быть сшито из двух попыток.

**Следствие.** Авто режим остаётся объявленным и заблокированным, пока нет раннера: предохранители
уже написаны и проверены, поэтому раннер будет исполнять готовое правило, а не изобретать его.

## ADR-022. Раннер исполняет готовое правило, а не заводит своё

**Принято 2026-11-24.** Раннер кампании — это код, который задаёт вопрос «какой шаг готов» плану,
проводит его той же функцией, что `pantheon step`, и спрашивает у правила повтора (ADR-021), можно
ли ещё попытку. Он ничего не решает сам: порядок шагов — порядок в файле плана, вердикт — Trajan,
коммит — после вердикта, повтор — по названной причине. Число итераций выводится из плана (сумма
попыток по шагам), а не задаётся константой в коде; поэтому «сколько можно» отвечает владелец в
файле, а раннер лишь не превышает. Прогон, который остановился, обязан назвать причину, записать
её в `run-*.json` и в fasti и выйти кодом 2; прогон без остановки — 0 только при вердикте
`complete`. Одиночная задача с `mode = "auto"` отказывает: автоматизация — свойство кампании,
у которой есть правило и учёт, а не флаг на одном прогоне.

**Почему.** Соблазн раннера — стать вторым местом, где живёт решение: свой список условий, свой
потолок, своя трактовка «готов». Тогда авто путь и ручной шаг начали бы расходиться, и вердикт
перестал бы быть единственным источником правды. Один код пути и один потолок, взятый из плана,
оставляют автономность скучной — а скучная автономность и есть надёжная.

**Следствие.** ADR-021 оставлял `auto` заблокированным, пока нет раннера; раннер появился и
использует то же правило, поэтому заглушка снята, а отказ одиночной auto-задачи остался — теперь
он говорит, куда идти (`pantheon advance`), а не «исполнителя нет».

## ADR-023. Авто-прогон начинает только с принятого дерева

**Принято 2026-11-24.** Перед первым шагом `pantheon advance` спрашивает у git, что в проекте не
закоммичено; если что-то есть, прогон не начинается, а называет пути. Ручной `pantheon step` этого
не требует: там решение принимает человек, который видит дерево. Черновик остановленной кампании
остаётся в дереве намеренно — его читают, прежде чем чинить; но следующий автоматический прогон не
должен судить чужую работу как свою.

**Почему.** Замер кодовых шагов (2026-11-24) дал ложный `hold`: в дереве остался файл от прошлой
остановленной кампании с незакрытой кавычкой, и `ruff`/`mypy` судили его, а не новое изменение.
Проверки судят дерево, а не только «HEAD плюс изменение», поэтому грязное дерево делает вердикт
неправдивым — а вердикт здесь и есть продукт. Отказ дешевле, чем доверие к ложному `hold`.

**Следствие.** Авто-прогон по проекту с рабочими правками — это не «пока нельзя», а «сначала реши,
что с ними»: закоммить, откатить или убрать. Пуш по-прежнему не входит, и запрет пуша не зависит от
этого решения.

## ADR-024. Повтор получает причину отказа

**Принято 2026-11-24.** Когда шаг повторяется, запрос исполнителю несёт блок `previous`: вердикт
прошлой попытки, проваленные проверки (с их сообщением) и находки с местом. Первая попытка получает
`null`; закрытый шаг причины не имеет. Оба исполнителя печатают эти строки в промпте под своим
заголовком, а не прячут в общий контекст. Заодно промпт говорит, что каждый файл заканчивается
переводом строки: это правило проекта, а не догадка модели.

**Почему.** Замер 2026-11-24 (`c-b1`) показал: вторая попытка написала верный код и верный тест, но
без завершающего перевода строки — и была остановлена линтером. Причина прошлого отказа модели не
сообщалась, поэтому повтор исправлял случайное. Повтор по D20 называется причиной; эта причина
должна доходить до того, кто будет исправлять.

**Следствие.** Повтор перестаёт быть «тем же запросом ещё раз» и становится ответом на конкретный
отказ. Это не ослабляет правило D20: решение о повторе по-прежнему принимает код, а модель получает
только факты записи — вердикт, проверки и находки, без чужих советов.

**Дополнено 2026-11-25.** То же для одиночной задачи: `pantheon resume --retry` собирает `previous`
той же функцией, что и шаг кампании, и перед повтором откатывает черновик прошлой попытки
(`caesar.revert`) — исполнитель читает файлы с диска и иначе прочитал бы отклонённое как проект.
Пилот нашёл это на `c-d4`: три повтора `c-d2` были слепыми (`previous` нёс `null`), потому что
зрячий повтор был проведён только через кампанию.

## ADR-025. Ворота пересчитывают заголовок патча по телу

**Принято 2026-11-24.** Перед применением ворота сверяют каждый заголовок хунка с его телом. Если
счёт не совпадает, заголовок пересчитывается по телу, применяется тело целиком, исходный дифф
модели кладётся рядом (`change.source.diff`), а причина попытки называет правку. `git apply
--recount` не используется: запись должна совпадать с деревом, поэтому пересчёт делает сам код и
пишет результат в `change.diff`.

**Почему.** Замер 2026-11-24: модель регулярно пишет в заголовке на единицу меньше строк, чем в
теле. `git apply` верит заголовку, молча выкидывает лишние строки и возвращает 0; `--check` тоже
возвращает 0. Поэтому `c-b1` и `c-k3` получили обрезанный файл и упали на проверках, хотя дифф был
верным, а замер записал это как «плохое качество патча». Ворота, которые применяют не то, что
написано в диффе, судят не тот файл — это тихий проход, запрещённый доктриной.

**Следствие.** Ошибка формата в заголовке больше не стоит попытки и не искажает вердикт. Тело
считается изменением: модель отвечает за то, что написала, а ворота — за то, чтобы применённое
совпало с записанным. Если владелец предпочтёт, чтобы формат чинила модель через повтор, это
заменяется отказом с причиной — пересчёт тогда снимается.

## ADR-026. Журнал чтения и потолок чтения на задачу

**Принято 2026-11-24.** Исполнитель отвечает блоком `reading`: сколько файлов и символов он
прочитал, оценку токенов, объявленный потолок и всё, что за ним осталось (имена файлов, обрезанные
файлы, нечитаемые файлы). Коробка записывает этот блок в `proposal.json`, в `dispatch-*.json`, в
вывод `pantheon dispatch`, в `pantheon status` и в acta. Задача или шаг кампании может объявить `max_read_chars`; потолок
переезжает в `limits` запроса, и исполнитель не читает сверх него: файл, который не влезает, не
читается наполовину — чтение останавливается, а остаток назван. Если потолок не вмещает ни одного
файла объёма, адаптер отвечает ошибкой до вызова модели: пустой запрос не отправляется.

**Почему.** Замер 2026-11-24: кодовый шаг стоил ~20 тыс. токенов, и по записи нельзя было сказать,
что именно попало в запрос, а урезание на 60 тыс. символов было видно только в промпте. Цена шага
росла вместе с объёмом `src/**`, и «почему дорого» оставалось догадкой. Журнал делает чтение таким
же фактом, как деньги: его можно посчитать и ограничить, а не обсуждать.

**Следствие.** У шага появляется честный, проверяемый предел чтения; всё оставленное названо, поэтому
модель и человек видят, чего модель не видела. Адресация записей по дайджесту (следующий шаг 3.2)
сокращает сам объём: журнал покажет, где чтение лишнее, и даст цифры для этого решения. Контейнерный
исполнитель чтение не наблюдает — его строка говорит «not reported», а не притворяется нулём.

## ADR-027. Адрес записи — часть протокола памяти

**Принято 2026-11-25.** У каждой записи в дайджесте есть адрес `<задача>/<время>`; он печатается в
`pantheon records`, в пакете и в записи прогона. Задача или шаг кампании может перечислить адреса в
`records`; коробка разрешает их по дайджесту до первого токена модели, неизвестный адрес — отказ,
названная запись входит в пакет с причиной «named by the task» и занимает одно из шести мест.

**Почему.** Отбор по путям — эвристика; шаг часто зависит от записи, чьи пути другие (формат,
решение, чужой модуль), и до сих пор единственным способом сказать это была правка эвристики. Адрес
превращает дайджест из списка в индекс: по нему можно сослаться, не объясняя путь. Проверка до
вызова модели важна: опечатка не должна стоить вызова и не должна тихо лишать пакет истории — тихий
пропуск здесь был бы тем самым «тихим проходом», который запрещён доктриной.

**Следствие.** Память проекта становится адресуемой для плана: автор плана может назвать запись,
которую считает решающей, а не надеяться, что эвристика по путям её найдёт. Больше шести названных —
отказ; адрес вне дайджеста (старше 200 записей) не адресуем, и это сказано. Адрес — не путь: файл
записи остаётся там, где лежит, и ещё раз его читать не нужно, пока модель не решит, что он решает
работу.

## ADR-028. Читатель читает только объявленные пути

**Принято 2026-11-25.** `persona/reviewer.toml` может объявить `when_paths`. Если ключа нет, читаются
все изменения, как раньше; если есть — читается только изменение, которое задевает хотя бы один из
объявленных путей. Решение принимается по путям из дифа, который применили ворота, до вызова
читателя. Пропуск не молчит: причина `not read by declaration (...)` попадает в вывод `dispatch`, в
запись (`review_skipped`), в acta и в список «чего мы не проверили», а `dispatch --json` отдаёт её
полем. `--review` на один прогон сильнее объявления.

**Почему.** Замер чтения (2026-11-24): на изменении, которое вводит поведение, читатель нашёл три
подтверждённые находки за 0,095 цента; на комментарии — ноль за 0,16; на заметке в `docs/` — ноль за
0,016. Читать документацию — платить за ноль, а выключать читателя целиком — терять находки на коде.
Объявленные пути выражают это одним полем профиля, не флагом на каждый прогон и не памятью человека.

**Следствие.** Экономия не выглядит как чтение: у пропуска есть причина, и она стоит там же, где
стоял бы вердикт читателя. Если изменение не задело объявленные пути из-за ошибки в путях профиля,
это видно как «не читали по объявлению», а не как «находок нет». Нет ключа — поведение прежнее,
поэтому старые профили не меняются; `status` печатает, какие пути читаются.

## ADR-029. Модель выбирается по виду задачи, тариф объявляется вместе с ней

**Принято 2026-11-25.** `persona/executor.toml` может объявить `[models.<вид>]` с полями `model`,
`price_in`, `price_out`. Harness выбирает модель до вызова по `kind` из задачи: запись для вида,
иначе `model` профиля. Выбранная модель уходит в запрос полем `model`, тариф — в окружение команды,
решение — в `proposal.json` (`model_choice`) и в событие `task.executed` (`data.model_choice`).
Тариф необязателен: без него окружение не переопределяется, и цена остаётся за командой. Одна
половина тарифа без второй — отказ профиля.

**Почему.** Вид задачи коробка уже объявляет и по нему уже гоняет пути и проверки; модель — тот же
вид решения, и держать его в профиле честнее, чем в памяти человека. Тариф идёт вместе с моделью,
потому что наш адаптер считает цену по объявленным ставкам: выбери дешёвую модель с дорогим
прайсом — и запись соврёт о деньгах, а потолок будет сравниваться с чужим числом.

**Следствие.** Решение видно в записи, а не только в поведении: `model_choice` говорит, взята ли
запись вида или профиль по умолчанию. Ценности без замера качества пока нет: механизм сделан, а
числа — дело набора задач из §09; закрытие 3.1 по «дешевле без падения качества» ждёт его.

## ADR-030. Чтение говорит, чего оно не увидело

**Принято 2026-11-25.** Траян рендерит промпт из дифа под потолок (120 КБ) и разбирает дифф под
потолок 200 КБ; всё, что не влезло, он называет в промпте строкой «not shown», а в отчёте — числом
показанных файлов и флагом `truncated`. Коробка читает эти поля и, если показанных файлов меньше,
чем тронутых путей изменения, пишет в «чего мы не проверили»: «читатель видел N из M файлов»; если
дифф обрезан при разборе — «изменение обрезано до чтения». Оба пробела независимы от пробела о цене:
усечённое чтение, счёт которого превысил потолок, называет оба.

**Почему.** «Файлов не найдено» и «файлов не показано» — разные факты, и в записи они выглядели
одинаково. Живой прогон: дифф 368 КБ, читатель увидел ноль файлов, вердикт при этом закрылся бы
как обычный `pass`, если бы проверки не упали по другой причине. Место для такой строки уже было —
раздел «чего мы не проверили», — не хватало только данных из отчёта.

**Следствие.** Пробел стал частью контракта чтения: усечение — это не «ноль находок», а названная
граница чтения. Число файлов в отчёте теперь значит «показано», а не «разобрано»; старые отчёты
читаются как раньше, потому что поле появилось раньше флага.

## ADR-031. Проверки выбираются под задачу, путь ставит нижнюю границу

**Принято 2026-11-25 (принцип); механизм по путям и счётчик долга сделаны, именованных наборов
нет.** Проверки проекта объявляют три набора —
быстрый, обычный, полный; задача объявляет, какой ей нужен; ворота отказывают, если набор ниже
нижней границы по путям (ядро, публичный API, рамка — только полный). Вердикт называет набор и то,
что не гонялось. Быстрые вердикты копят долг: после N или после смены направления следующий прогон
полный. Сделано: `status` показывает долг, после пяти узких вердиктов следующий `dispatch`
проверяет полную политику; повторный вердикт не считается дважды.

**Почему.** Полный набор на правку одного файла — не надёжность, а шум. У корня Пантеона `make check`
гоняет 988 тестов на любую правку и занимает около двух с половиной минут, тогда как вызов модели —
12 секунд. Выигрыш даёт не «меньше проверок», а «только относящиеся к делу»: чужие сюиты эту правку
не проверяют, они просто жгут время.

**Следствие.** «Зелёный» перестаёт быть одним словом: у него появляется область. Полный набор
остаётся контрольной точкой — перед пушем, после смены направления, после накопленного долга. Если
проект объявил только полный набор, поведение прежнее. Замер скорости — `pilot/speed.md`; пока чисел
нет, механизм не считается доказанным.

## ADR-032. Непрерывная работа — поток, а не сумма задач

**Принято 2026-11-25 (принцип); бриф, лента и очередь сделаны, демона нет.** Непрерывная работа ведётся потоком: бриф (что
строим и зачем) и лента попыток. Отброшенный подход — запись с причиной; вердикты падают в очередь и
читаются позже. Кампания — частный случай: план, шаги, ревизии, раннер; поток — план, который
меняется по ходу.

**Почему.** В непрерывной работе направление меняется: фича внедряется на ходу, подход отбрасывается,
к прежнему возвращаются частично. Если каждая попытка — отдельная задача, история рассыпается, и
следующий агент (или владелец через неделю) повторяет уже проваленный опыт. Чат помнит разговор, но не
помнит лабиринт; коробка должна помнить лабиринт.

**Следствие.** Единица записи — поток, а не задача: вердикты остаются, но читаются в контексте «что мы
строим и что уже отбросили». Синхронный `dispatch` для потока не годится — нужна очередь. Механика
ревизий уже есть (D16); добавляется запись направления.

**Механизм 2026-11-25.** Бриф (`--brief` + `--why` + `--milestone`) пишется в
`tabularium/fluxus/brief.toml` и проверяется утверждённой рамкой; очередь — замороженные копии задач в
`tabularium/fluxus/queue/`; `--next` гоняет старейшую тем же `dispatch` под замком и пишет вердикт в
ленту `feed.jsonl`; `--discard` пишет причину отброшенного подхода; `--mark-read` — событие. Фонового
работника нет: `--next` запускает оператор.

## ADR-033. R&D-цикл — универсальная схема «вопрос → эксперимент → прогон»

**Принято 2026-11-25.** Исследование объявляет вопрос и бюджет; эксперимент — гипотезу с
предсказанием, необязательное изменение, матрицу прогонов (параметры × повторы), метрики с единицей,
направлением и порогом, ресурсы (инструменты, данные, модели, воркеры) и бюджет; прогон — команду,
чей вывод коробка хранит и из которой извлекает числа. Код сравнивает числа с порогами и по
объявленному правилу выбирает следующий эксперимент или закрывает вопрос. Смена вопроса, порога или
графа — решение владельца.

**Механизм 2026-11-25.** Исследование — `.pantheon/studia/<id>.toml`; прогон — `pantheon study --run`:
матрица параметров и повторов, команды в объявленном cwd/окружении, числа вынимаются шаблоном, агрегат
объявлен заранее, порог даёт вердикт гипотезе, таблица `on_confirmed`/`on_refuted` — следующий шаг.
Прогон без числа — `failed`, а не `refuted`. Эксперимент пока не объявляет изменение, поэтому вердикт
кода — «не гонялся»; деньги — только число, напечатанное командой.

**Почему.** Большая задача не закрывается одним проходом: сначала гипотеза, потом прогон, потом
число, и только потом решение. Схема универсальна, потому что не знает предмета — только прогоны,
числа и сравнения; доменное остаётся в проекте командами. Это не отдельный evaluation-корпус, а та же
дисциплина «ожидание до прогона», применённая к другому предмету.

**Следствие.** У эксперимента два вердикта: проверки кода и судьба гипотезы. Опровергнутая гипотеза
при зелёных проверках — успех цикла. Отброшенная ветка остаётся в записи. Внутри цикла каждый прогон —
обычный: тот же исполнитель, ворота, проверки и запись; нового исполнителя нет.

## ADR-034. Пантеон — harness для владельца: рамка и рельсы

**Принято 2026-11-25 (направление); рамка и утверждение сделаны.** Система ведёт не только изменение агента,
но и процесс владельца. Онбординг проекта — разговор по пунктам; результат — рамка: бриф, цели, вехи,
метрики, принципы, архитектурная модель и требования, — в репозитории, утверждение — записью в
коробке. Задача называет веху, которой служит; работа без вехи отклоняется. Отступление от рамки —
одна из трёх ревизий: дополнить, переписать, пересмотреть; тяжёлые требуют записки о риске и
повторного утверждения. Ответ «на усмотрение» — это ответ: коробка берёт умолчание и записывает
делегирование.

**Почему.** Без рельсов harness превращается в ускоритель куража: агент охотно делает то, что
попросили, а проект уезжает в сторону — одна задача тянет вторую, подход меняется, сделанное
бросается. Рельсы не запрещают менять направление; они требуют, чтобы изменение направления было
решением с названной ценой, а не побочным эффектом.

**Следствие.** Появляется второй контур — governance: рамка, вехи, ревизии, вопросы. Он не отменяет
первый (задача → вердикт) и не замедляет его: быстрый набор живёт внутри рельсов, а вопрос задаётся
при онбординге и при ревизии, не на каждой задаче. Рельсы держат только то, что проходит через
коробку; прямые правки мимо — открытый вопрос, записанный в `docs/12-rails.md`.

**Механизм 2026-11-25.** Рамка — `.pantheon/rails.toml` (бриф, цели, вехи, метрики, принципы);
`pantheon rails` показывает её и называет незаполненное, `pantheon rails --approve` пишет запись с
отпечатком и принятыми делегированиями. Утверждение отказывает, пока нет брифа, цели, вехи или
метрики: утверждать нечего. Задача объявляет `milestone`; утверждённая рамка отказывает задаче без
вехи и задаче с вехой, которой нет в рамке; `outside_plan` записывает причину выхода из плана.
Если рамка не утверждена, задача идёт, а пробел назван в записи. Отступление от рамки — запись
ревизии: `add` (лёгкая), `replace` и `revisit` (тяжёлые, с ответами «что сломается» и «что
потеряем»); тяжёлая ревизия не пускает задачи, пока новая рамка не принята, а прежние задачи
перечислены в записи.

## ADR-035. Жёсткость без обрезания: две проверки у задачи

**Принято 2026-11-25.** Коробка держит три вещи сразу и не жертвует ни одной: жёсткость (вердикт
считает код, а не модель), проверяемость (у каждой правки есть проверка, которая её судит) и
контроль (модель не подгоняет ответ под то, чем её судят). Четвёртое, что нельзя потерять, — место
для работы: агент, у которого нет ни одного видимого признака «готово», пишет вслепую и тратит
попытки на угадывание.

Решением стало разделить проверки по роли. У задачи есть скрытая проверка (`repro`): она гоняется
до изменения, прикладывается к политике и выносит вердикт — модель её не видит. И есть видимая
(`self_check`): она показывается исполнителю в запросе, коробка прогоняет её после изменения и
записывает результат рядом с вердиктом, но в вердикт она не входит никогда. Обе проверяют одно и то
же поведение на разных данных: подгонка под видимую умирает на скрытой, а признак этого — «видимая
зелёная, скрытая нет» — попадает в запись отдельной строкой и в факты повтора.

В запросе исполнителя видимая проверка стоит с прямым объяснением: её видно, а судит другая.
Повтор получает слова видимой проверки, а не скрытой: иначе вторая проверка стала бы первой, и
смысл разделения исчез бы на второй попытке.

**Почему.** Пилот 2026-11-25 (`c-d4`, `c-d4b`, `c-d5`) показал: модель, работающая с
инструментами (тот же `deepseek-flash`, что пишет этот репозиторий), задачу решает, а исполнитель с
одним выстрелом и без рук — нет. Ответы были верны по идее (331–495 токенов) и падали там, где
нужно увидеть результат. При этом «просто показать модели проверку, которой её судят» — это ровно та
подгонка, ради запрета которой проверки и считает код (D8, D25).

**Следствие.** Задача дефекта теперь несёт две проверки, и это работа автора задачи: видимая должна
быть честной (правка, проходящая скрытую, проходит и её), а скрытая — сильнее по данным (другие
значения, другой вход), иначе она пропустит подгонку. Расхождение проверок — не ошибка коробки, а
факт: он записывается, называется в отчёте и попадает в факты следующей попытки.

## ADR-036. Форма задачи задаёт бюджет, а не один потолок на всё

**Принято 2026-11-25.** У задачи появилось поле `shape`: `patch` — несколько строк в названных
местах, `file` — один файл целиком, `multi` — несколько файлов. Коробка объявляет таблицу
`[shapes.<форма>]` с потолком ответа и, если нужно, ценой; задача может просить только меньше, а
форма, которой у коробки нет, — отказ до вызова модели. В запрос форма уходит и словами: модель
знает, какого размера ответа от неё ждут, и вправе ответить `ERROR:`, если правка в эту форму не
влезает.

**Почему.** Пилот 2026-11-25 показал провал не по незнанию, а по масштабу: на задачу, где нужно
несколько строк, модель отвечала попыткой переписать файл целиком (24 и 44 копии первого хунка,
4 096 токенов в потолок). Один потолок ответа на все задачи — это либо обрезка (маленькая задача
получает маленький ответ, который не влезает), либо трата (большая задача получает маленький
потолок и повторяет). Решение — объявлять размер заранее, как бюджет, и держать ответ в его рамках.

**Следствие.** Оценка сложности становится частью задачи и проверяется записью: в отчёте есть
объявленная форма и её потолок, а оборванный ответ и `ERROR:` от модели — два вида «оценка была
неверна». Потолок ответа больше не зависит от переменной окружения: у формы свой, у коробки —
свой на случай, когда форма не объявлена.

**Дополнено в тот же день (жёсткость на выходе).** Словами форма модель не убеждает: `c-d7` с
`shape = "patch"` и фразой «файл не переписывать» всё равно ответил пересказом файла. Поэтому у
формы появились границы — `max_changed_lines` и `max_files`, объявленные коробкой: ответ, который
больше объявленного, ворота называют «не в форме», не применяют и передают оба числа в запись и в
факты повтора. Это вторая половина схемы: форма — не только потолок размера ответа, но и правило,
по которому ответ принимается или нет, и проверить его может только код, а не модель.

## ADR-037. Бюджет задачи — сумма, попытки считаются, повтор без прогресса останавливается

**Принято 2026-11-25.** `budget.max_cents` задачи — потолок на всю задачу, а не на попытку. Harness
складывает цену сделанных вызовов по `proposal.json` (вызов, не назвавший цену, считается по потолку
коробки, а если потолка нет — сумма называется нижней оценкой), и следующий вызов получает только
остаток: `limits.max_cents` в запросе — это остаток, а не объявленный бюджет. У задачи появился
`max_steps`, у коробки — такой же ключ; действует минимум. Перед вызовом задача может остановиться:
`state = "stopped"`, `stop_reason` и код возврата 2 — по исчерпанному бюджету, по числу вызовов или
когда две применённые попытки подряд провалили видимую проверку с одним кодом и одними и теми же
словами. Результат видимой проверки пишется рядом с попыткой
(`tabularium/<task>/<n>/self-check.json`), а не только в запись прогона: у попытки свой номер, и
две записи в одну секунду её не перезапишут.

**Почему.** Пилот на click: восемь попыток на один дефект стоили 12,3 цента при потолке 2–3 на
вызов. Каждая попытка получала бюджет задачи заново, потому что бюджет жил в контракте попытки, а не
в задаче; ограничить было нечем, кроме числа попыток у кампании, а у одиночной задачи не было и его.
«Стоп по деньгам» работал только на один вызов.

**Следствие.** Восемь попыток на задачу с бюджетом 3 цента теперь стоят не больше 3 центов, а
девятая не начинается. Задача, которая получает тот же провал видимой проверки, останавливается
сама, а не ждёт, пока кончится бюджет: «нет прогресса» — это факт из двух попыток, а не мнение
модели. Остановка — не вердикт: задача не закрыта и не возвращена, она остановлена с причиной, и
`resume` продолжает её с артефактов. Правило приёмки не изменилось: вердикт по-прежнему считает
Trajan.

**Чего это не меняет.** Потолок одного вызова остаётся у коробки и формы; задача может просить
меньше. «Сколько осталось» не хранится отдельным счётчиком: оно считается по записям, так что
забытого или подделанного счётчика не бывает. Цена чтения изменения входит в сумму задачи по записи
прогона; вызов без цены не считается бесплатным — он считается по потолку, а если потолка нет, это
называется в причине остановки.

**Найдено при реализации, не исправлено.** Две записи `dispatch-<время>.json` в одну секунду
пишутся в один файл: вторая затирает первую. На реальном прогоне это редкость, в тестах — обычное
дело; поэтому сигнал «нет прогресса» читает файлы попыток, а не записи прогонов. Сама потеря записи
— отдельный дефект, он записан в handoff и ждёт решения. Сводка в `acta/` одна на задачу в день —
это задумано: история живёт в записях, acta — то, что читает владелец.

## ADR-038. Два движка: один ответ и шаги, и оба через одни ворота

**Принято 2026-11-25.** У коробки два движка исполнения, объявленных таблицей `[engines.<вид>]` в
`persona/executor.toml`: `one-shot` спрашивает один раз и живёт с ответом, `steps` применяет ответ,
гоняет видимую проверку задачи и спрашивает снова. Движок выбирается по `kind` задачи, как модель
(D30), и решение пишется в `proposal.json` (`engine`, `engine_choice`) и в запись (`engine`). Шагу
нужен потолок вызовов — `max_steps` задачи или коробки; без него `steps` отказывается до первого
вызова. Протокол один и тот же плюс `turn` и `turns`: номер вызова и короткая история прошлых шагов
(что ворота сделали с ответом, что сказала видимая проверка). Ответ может сказать `done` — работа
закончена, диффа нет.

**Почему.** Пилот на click показал предел одного вызова: модель не видит, что её правка сделала с
поведением, и восемь попыток подряд упирались в один и тот же провал. Под мелкую задачу дешёвый
одноразовый вызов остаётся правильным; под комплексную нужен агент, который читает, пробует,
видит результат и поправляется. Второй режим не отменяет первый и не заводит второго писателя:
каждый шаг проходит через Caesar, а вердикт по-прежнему считает Trajan по накопленному дереву.

**Почему не рабочая копия с финальным диффом.** Копия дала бы агенту свободу, но превратила бы
контроль из запрета в обнаружение: проект меняется в копии, ворота видят один большой дифф в конце,
дрейф виден поздно, и появляется второе дерево для синхронизации. Шаги через ворота дают то же
свойство дешевле: отказ ворот виден следующему шагу как факт, а не как сюрприз в конце.

**Следствие.** Остановки цикла детерминированы и считаются из записей: потолок вызовов, остаток
бюджета, две применённые попытки с одинаковым провалом видимой проверки, повтор уже применённого
диффа, ответ без патча или `done`, отказ ворот, видимая проверка прошла. Остановка не отменяет
вердикт: если хотя бы один шаг применён, `verify` считается по накопленному дереву, а `stop_reason`
остаётся в записи; `state = stopped` и код 2 — только когда менять нечего. Коммит после `pass`
собирается из всех применённых шагов по порядку, тем же `git apply` в временный индекс. `resume`
без `--retry` продолжает незаконченный цикл по записям, `resume --retry` откатывает все шаги
последнего прогона (последний первым) и пишет `reverted.json`.

**Чего это не даёт.** Модель не запускает своих команд и не пишет в проект: инструменты шага —
прочитать проект, предложить дифф, увидеть хвост объявленной проверки; всё остальное делает коробка.
Цена растёт с числом шагов — её ограничивают бюджеты ADR-037, а не оптимизм. Живой прогон c-d10
сделан 2026-11-25 и провален: четыре вызова, ни одного применённого, 4,03 цента — `deepseek-flash`
истратил потолок ответа на размышление и не вернул текста, и в `steps`, и в контрольном `one-shot`.
Причина измерена 2026-11-26 (см. `docs/09-evaluation.md`): на это задание модель тратит 17 402
токена размышления, а потолок был 8 192; с комнатой 32 768 она заканчивает сама и даёт дифф,
проходящий обе проверки. После перехода на денежную комнату (ADR-039) живой `c-d11` прошёл
2026-11-26 за один шаг: 15 498 размышления + 250 ответа, 1,95 цента, pass по `repro`. Механика
цикла проверена и живым прогоном, и тестами; следующий вопрос — не устройство цикла.

## ADR-039. Деньги — бюджет, комната вызова — производная

**Принято 2026-11-26.** Единственная бюджетная ручка задачи — деньги (`max_cents`) и время; комната
ответа не объявляется формой изменения и не задаётся константой. Перед вызовом коробка считает её
из остатка: минус резерв (на шагах четверть, у `one-shot` десятая часть, не меньше 0,5 цента и
стоимости промпта), остаток переводится в токены по цене выхода модели и обрезается потолком
провайдера (`max_output_tokens` в профиле модели или коробки). Если цена не объявлена, комната
равна потолку провайдера, и запись говорит, что цена не ограничена до вызова; если денег не
хватает на полезный вызов — запись `insufficient-budget` и никакого вызова. Форма
(`[shapes.<форма>]`) теперь объявляет только масштаб изменения (`max_changed_lines`, `max_files`),
не комнату и не цену.

**Почему.** Живой c-d10 показал, что технический потолок токенов, выбранный заранее, определяет,
какие задачи модель вообще может решить: на этом endpoint размышление входит в `max_tokens`, модель
тратит 17 402 токена на задачу, а форма давала 8 192 — обрыв на середине мысли, четыре пустых
ответа, 4,03 цента. Токены — это деньги в другой единице; бюджет должен быть деньгами, а комната —
их переводом, иначе каждая новая модель требует новой калибровки одной и той же таблицы.

**Почему не «один адаптивный повтор на обрыв».** При денежной комнате обрыв означает, что комната
израсходована до последнего токена, а остаток бюджета — это резерв, из которого выходит только
меньшая комната. Повтор в том же бюджете не может дать больше места; он купит меньше и оборвётся
снова. Поэтому коробка не делает вид, что повторяет: она записывает `finish_reason`, комнату и
`reasoning_tokens` и говорит, что большая комната — решение о бюджете (`resume` с поднятым
`max_cents` — уже новый бюджет). Это проверено арифметикой и тестом на комнату.

**Следствие.** В `proposal.json` появились `finish_reason`, `billing_status` (`billed`,
`not_billed`, `unknown`), `max_tokens` и `truncated`; в `usage` — `reasoning_tokens` и
`answer_tokens`. `spent` не считает `not_billed` ни деньгами, ни вызовом: вызов без ключа больше
не съедает бюджет. `limits.max_answer_tokens` — вычисленная комната, а не форма;
`PANTHEON_MODEL_MAX_TOKENS` остаётся только для прямого вызова без коробки. Приёмка «не меньше двух
шагов» снята: успешный один шаг — успешное исполнение `steps`, а продолжение цикла проверяется
детерминированным тестом, а не заставлением живой модели делать лишний шаг.

**Чего это не даёт.** Комната не гарантирует, что модель закончит: она гарантирует, что вызов не
потратит больше, чем осталось, и что обрыв будет виден с причиной. Большая задача по-прежнему
дробится на шаги или задачи: форма разрешает 4 000 строк, но комната считается из денег, и если их
не хватает — это `insufficient-budget` или `truncated`, а не тихая половина правки.

**Живая проверка 2026-11-26.** `c-d11` — та же задача, что `c-d10`, с бюджетом 6 центов и профилем
без потолка в форме: один шаг, `finish_reason=stop`, 15 498 размышления и 250 ответа, 1,95 цента,
64,2 с; ворота применили дифф мягким проходом, видимая проверка и `repro` прошли, коммит `2abb654`.
Приёмка D выполнена, этап 4 закрыт.

**Уточнение 2026-11-26 (нашла живая приёмка B/C).** Потолок коробки (`max_cents` в профиле) —
не только строка в выводе: `_guard` берёт минимум из бюджета задачи и потолка коробки, поэтому
задача, просящая больше, тратит не больше коробки, а задача без своего бюджета всё равно ограничена
коробкой. Преемник `c-d11-b` попросил 8 центов при коробке 6: `explain` показал лимит 6, комнату из
6 и строку «the box's ceiling is what binds»; без этого `dispatch` считал бы комнату из 8.

## ADR-040. Конверт правится преемником, объяснение читает те же функции

**Принято 2026-11-26.** Задача не меняется под своей записью. `pantheon amend --task <id> --why
"..." [--add-path ...] [--budget key=value ...] [--max-steps N]` пишет новую задачу `<id>-b`
(следующая свободная), у неё `parent`, `why`, и `tabularium/<id>-b/amendment.json` с разницей по
путям, бюджету и потолку вызовов. Родитель получает событие `task.amended`, `amendments.json` со
всеми преемниками и строку «replaced by …» в `status` и acta; acta преемника печатает раздел «what
changed from the parent». Преемник наследует объявленный патч родителя, но не его попытки и не его
вердикт. Пустая разница — отказ: преемник без изменения — то же имя для той же задачи.

`pantheon park --task <id> --why "..."` пишет `parked.json`: задача остаётся читаемой, а
`dispatch` и `resume` отказывают до появления преемника. Парк — не пауза: вернуться можно только
новой задачей (`amend`), а старый вердикт и цена остаются на месте.

`pantheon explain --task <файл|id>` — read-only резолвер: рамка, рельсы, маршрут с воротами записи,
движок и модель, лимиты (секунды, центы, вызовы), комната из остатка, проверки политики, `repro`,
`self_check`, читатель и пробелы. Он не пишет ни записи, ни контракта, ни события; для этого он
зовёт те же `route`, `_with_write_gate`, `engine_for`, `model_for`, `limits`, `_guard` и `room_for`,
что и `dispatch`, и тест «объяснение равно записи» держит их вместе.

**Почему.** Расширение задачи жило только в голове владельца: новая задача без связи с прежней,
причина нигде, и `status` показывал два несвязанных следа. Отложенная задача не имела состояния
вовсе: её можно было случайно запустить, а потом гадать, почему она не должна была идти. `explain`
закрывает обратную сторону: до вызова видно, что разрешено, что будет проверено и что останется
непроверенным, — и это видно теми же словами, которыми потом говорит запись.

**Чего это не даёт.** `explain` не предсказывает цену и вердикт: он читает правила, а не ответ
модели; комната — оценка из остатка, а не гарантия. `park` не удаляет и не отменяет уже
потраченное; это запись решения, а не откат. Цепочка родителей — данные, а не автоматическое
слияние: преемник наследует патч родителя, но не его попытки и не его вердикт.

## ADR-041. Уровень исполнения выбирается до вызова: one-shot — исключение

**Принято 2026-11-26.** Коробка объявляет таблицу `[execution]`:
`one_shot_max_files`, `one_shot_max_changed_lines`, `steps_max_files`,
`steps_max_changed_lines`. Если таблица объявлена, задача получает уровень до вызова модели:

- **L1 — one-shot.** `shape = "patch"`, нет `self_check`, путей не больше
  `one_shot_max_files`, и форма не разрешает больше `one_shot_max_changed_lines` строк. Один
  вызов: писать сразу, проверять после.
- **L2 — steps.** Есть `self_check` — видимая проверка, которая падает до правки; путей не
  больше `steps_max_files`; форма не разрешает больше `steps_max_changed_lines` строк; есть
  потолок вызовов (`max_steps` задачи или профиля). Цикл: применил, прогнал, спросил снова.
- **L3 — агент.** Всё остальное: больше файлов или строк, `file`/`multi` без видимой проверки,
  неизвестная форма, steps без потолка. Агента в коробке ещё нет, поэтому L3 — отказ
  `needs-agent`, а не тихий one-shot.

Явная таблица `[engines.<вид>]` может сделать исполнение **тяжелее**, но не легче: `steps` на
L1 разрешён (коробка так решила), `one-shot` на L2 повышается до `steps`, L3 не запускается
никогда. Коробка без `[execution]` сохраняет старую таблицу движков; `explain` называет это
пробелом, потому что граница не enforced.

**Почему.** E2 (2026-11-26) показал, что one-shot решает маленький `e-r1`, но на `e-r2`/`e-r3`
(3 файла, около 100 строк) все три режима провалились: C тратил 32 768 токенов на размышление
и не возвращал патч, A/B давали неприменимые диффы. Ни один провал C не дошёл до проверок — он
умирал на ответе модели. Это не довод против коробки: это довод за то, что одному вызову
нельзя давать задачу, где нужен цикл «применил — прогнал — поправил». Выключение размышления
(E2b) сделало хуже: контрольный `e-r1` сломался, модель стала писать огромный патч. Значит,
рычаг — не «думать/не думать», а уровень исполнения и форма ответа.

**Следствие.** В `Dispatch` и `Explanation` появились `level` и `route_reason`; `explain`
печатает уровень до вызова, `dispatch --json` его записывает. L3 отказывает до создания
контракта и вызова, с причиной, называющей файлы/строки/отсутствие проверки. Пороги — стартовые
и меняются только записью: цифры в таблице не догма, догма — «one-shot не запускается выше L1».
`self_check` остаётся видимой проверкой: он выбирает цикл, но вердикт по-прежнему у `repro`.

**Чего это не даёт.** L2 не гарантирует, что steps решат задачу: видимая проверка может быть
слабой, а модель — не справиться; тогда это `returned` или L3. L3 пока отказ, а не работа:
агент с инструментами — следующий контур, и до него граница честно говорит «needs-agent».

## ADR-042. Размышление — не рычаг, уровень — не рычаг; агент запускается через те же ворота

**Принято 2026-11-26.** Вопрос «поднять потолок и всё поедет» закрыт тремя замерами, и ни один
из них не дал рычага:

- `c-d10` (2026-11-25): задаче требовалось 17 402 токена размышления; в комнате 8 192 модель
  вернула пусто. Когда комната стала считаться из денег (D40), та же задача решилась за один шаг:
  15 498 размышления + 250 ответа.
- E2b (2026-11-26): размышление выключили — контрольный `e-t1`, который решался, сломался;
  остальные не улучшились.
- L2 живым прогоном (2026-11-26): `e-r2` в `level 2`/`steps`, один вызов, 32 768 токенов ушло в
  размышление, текста ноль; шаг `truncated`, дерево цело. Обрыв терминален, второго шага не было.
- `deepseek-chat` (round 5): запрос назвал модель без размышления, endpoint ответил именем
  `deepseek-flash` и без `reasoning_tokens`; три вызова, 4,73¢: первый шаг применился и провалил
  видимую проверку, второй отказ ворот (патч не лёг), третий обрезан на 24 165 токенах ответа.
  Не решено. Имя модели в записи — то, что ответил endpoint; расхождение запроса и ответа
  записано как факт, а не сглажено.

**Решение.**

1. Размышление остаётся включённым по умолчанию. Это не «лишний расход», а то, как эта модель
   планирует дифф; выключение не лечит и ломает уже решённое. `PANTHEON_MODEL_THINKING` остаётся
   диагностическим переключателем и в продукте не включается.
2. Комната вызова считается из денег (D40) и обрезается потолком провайдера. Потолки не
   подбираем и не поднимаем: 32 768 — предел, выше некуда.
3. Граница L1/L2/L3 остаётся **страховкой, а не рычагом**: one-shot не запускается выше L1, L2
   не развиваем, пока не появится агент. `steps` остаётся в коде — объявлен, покрыт тестами,
   живой цикл видел, — но новых порогов и шаговых эвристик не добавляем.
4. Следующий исполнитель — **агент** (L3). Он запускается не как новый control plane, а как
   движок коробки: та же задача, тот же контракт, те же ворота, тот же вердикт кодом. Модель
   получает маленький набор инструментов — прочитать, прогнать видимую проверку, предложить
   правку — и каждый её шаг исполняет **коробка**, а не процесс-исполнитель. Поэтому агент не
   владеет деревом и не пишет мимо ворот: всё, что он сделал, попадает в `tabularium`, а
   отказ ворот посреди работы — нормальный факт, а не сбой.
5. Сдерживание — собственность и запись, а не количество ограничений. Пути, форма и проверки
   объявлены задачей; рамка и рельсы держат направление; деньги — единственный жёсткий предел,
   который добавляет коробка; остановка — по факту (видимая проверка прошла, прогресса нет,
   бюджет кончился), а не по «N шагов». `max_steps` остаётся страховкой от зацикливания, не
   планом работы.

**Чего это не даёт.** Агента ещё нет: L3 — отказ, а не тихая работа. Решение фиксирует, как он
будет запускаться, чтобы следующая сессия не пересобирала те же аргументы; постройка — отдельная
работа, и до неё границы и комнаты не двигаем. Один живой `deepseek-chat`-прогон не доказывает
«модель без размышления решает»: он не решил, а имя модели в ответе endpoint'а разошлось с
запросом — это ограничение замера, записанное рядом с числом.

## ADR-043. Сценарий «ремонт»: критерий — живая падающая проверка, и это не весь продукт

**Принято 2026-11-26.** Все живые кейсы до сих пор — ремонт: дефект есть сейчас, его можно
воспроизвести командой, которая падает. Для этого сценария фиксируется критерий сделанности.

1. **Критерий — `repro` задачи**: команда, которая падает на базе и проходит на известном фиксе.
   Объём (`paths`, `shape`) — только граница правки, не доказательство, что задача настоящая.
   Проверки политики по тронутым путям — регрессия: «не сломали то, что работало». Вердикт =
   `repro` + эти проверки.
2. **`repro` зелёный на базе** — задача не «уже сделана», а «не описывает живого дефекта»: в
   работу не идёт (или проверка переписывается). Baseline должен быть зелёным: красный suite
   по другой причине не доказывает, что чинили именно это.
3. **Это правило только для ремонта.** Достройка (фича, новая возможность) — другой сценарий:
   падающего дефекта нет, есть требование и отсутствующее поведение. Там критерий — спецификация,
   написанная до работы и красная потому, что поведения ещё нет; плюс приёмка владельца, что
   спецификация — то, что нужно; плюс старый suite. «Реальность» задачи проверяется требованием,
   а не падением.
4. **Не смешивать.** Один набор правил на оба сценария сделает хуже обоим: фичи начнут требовать
   искусственно падающий тест (и придумывать дефект), а ремонт — принимать «зелёный тест» за
   доказательство, что дефект был.

**Почему.** В пилоте критерий реальности был именно таким: скрытые проверки `e-r1`/`e-r2`
падали на базе и проходили на фиксе; `e-r4` без падающей проверки проверял ворота, а не задачу.
В `explain` и acta это уже видно по наличию `repro`: нет проверки — «done rests on the suite»,
а не «дефект исправлен». Нового поля не нужно; сценарий читается из объявленной проверки.

**Следствие.** «Проверка проверки» (preflight) — часть ремонтного сценария: `repro` на базе
падает, на эталонном фиксе проходит. Для достройки эталона нет, и preflight будет другим —
поэтому фичевый flow описывается отдельным решением, когда возьмём первую фичу, а не сейчас.

## ADR-044. Контракт задачи: критерий выводится до работы, без него задача не стартует

**Принято 2026-11-26.** Репетиция трёх отчётов (2026-11-26) показала: исполнение измерено, а узкое
место — критерий. Отчёт может быть неопределённым, а критерий — подменённым; пока критерий не
зафиксирован, любая правка «не та», и цикл не кончается.

1. **Контракт задачи** пишется до любых тестов и правок и состоит из пяти пунктов: симптом (что
   видно, словами владельца), ожидаемое поведение (наблюдаемое), как это видно (команда, место,
   действие), границы (что нельзя менять), недостающие факты (вопросы владельцу). В файле задачи
   ожидаемое поведение — существующее поле `expected`; остальные четыре пункта — таблица
   `[contract]` с полями `symptom`, `visible`, `boundaries`, `missing`. Контракт замораживается
   снимком задачи вместе с ней.
2. **Критерий выводится из слов** — разговора с владельцем или отчёта. Чтение репозитория
   разрешено только чтобы ответить «как мы узнаем, что починили» (существует ли названное,
   наблюдаемо ли, где видно), а не «почему сломалось»; причина — работа репродьюсера.
3. **Лестница контекста**: разговор → слова отчёта → карта (индекс файлов, команд и тестов, без
   содержимого) → срез файлов → полное чтение ради критерия. Спуск — только за названным фактом;
   нет названного факта — нет чтения. Полное чтение — последняя ступень оркестратора, и его цель
   ровно критерий, а не исследование.
4. **Без контракта задача в работу не отдаётся.** Если критерий не выводится даже после полного
   чтения — эскалация владельцу с конкретными вопросами; догадка в работу не идёт.
5. **Контракт замораживается** до начала работы. Сменить его может только владелец отдельной
   записью; провал попытки — факт о правке, а не повод менять цель.
6. **Репродьюсер получает контракт** и пишет проверку; если по контракту проверку написать
   нельзя — возвращает «контракт не фальсифицируем», а не выдумывает тест. Валидатор судит диф
   против отчёта, а не против того, что оркестратор увидел в коде.

**Почему.** В первом кейсе репетиции код-вердикт принял правку «ADR-001…043 и далее», потому что
критерий проверял только числа, а требование — «включая последнее». Во втором критерий прошёл и на
фиксе ремонтника, и на историческом эталоне, но валидатор нашёл, что `resume` снова теряет
уровень. В третьем расплывчатый отчёт дал отказ с перечнем недостающих фактов. Во всех трёх провал
был не в исполнении, а в том, что критерий и требование разошлись.

**Следствие.** На задачу добавляется один вызов (контракт) и, когда слов мало, чтение ради
критерия; эскалаций станет больше. Метрика постановки — доля эскалаций: ноль значит, что
оркестратор выдумывает критерий; слишком много — что отчёты плохие. Правило D44 («критерий —
живая падающая проверка») не отменяется: контракт говорит, **что** проверять, `repro` — **чем**.

Пункт 4 теперь ворота, а не намерение: `dispatch` задаёт вопрос `intake` до любых контуров и
отказывает задаче без контракта событием `task.refused` — до оплаты и без записи попытки. План
кампании несёт тот же контракт у каждого шага (`[step.contract]`), и шаг без него называется
проблемой плана до старта.

**Третья отметка.** Приёмка называлась тремя отметками, а записывалась только первая (код) и, при
объявленном читателе, вторая (причина). `pantheon accept <box> <задача>/<метка> [--note] [--reject]`
пишет решение владельца рядом с архивной правкой: кто, когда, про какой дифф и коммит. `history`
показывает отметку, а без неё — «владелец ещё не решил», потому что отсутствие решения тоже факт.
Адрес без закрытой правки отвергается; та же отметка дважды не становится вторым решением; позднее
«нет» идёт за ранним «да» — файл хранит все отметки по порядку, а не последнюю вместо всех.

## ADR-045. Архив правок: история причин, а не история коммитов

**Принято 2026-11-26.** Коммит говорит, что изменилось, но не почему и чем проверяли. Когда
правок много, костыли начинают конфликтовать, и разобрать конфликт по истории коммитов нельзя:
у коммита нет контракта, падающей проверки, замечания валидатора и отброшенных вариантов. Плюс
история коммитов переписывается, а причины остаются.

1. **Единица архива — правка с причиной:** контракт и отчёт, дифф, обе проверки с хешами, вердикт,
   замечание валидатора, отклонённые попытки (дифф, класс отказа, одна фраза почему), цена и
   время, тронутые пути.
2. **Триггер — закрытие правки (коммит), не пуш:** пуш может не случиться, а факт закрытия уже есть.
3. **Проекция, не журнал.** Архив собирается из записи коробки при закрытии, руками не пишется.
   Источник истины о дереве — репозиторий, о причинах — архив; второй правдой о коде он не
   становится.
4. **Живёт в коробке проекта**, не в репозитории; индекс — по путям и по времени.
5. **Читателей три:** рефакторинг (карта модуля: какие правки, зачем, что отменяют друг друга),
   разбор конфликта (какие правки трогали обе стороны и когда), репродьюсер (что уже меняли в этих
   путях и почему). Запрос ограничен: правки по путям из карты, контракт и вердикт; дифф — по
   требованию. Чтение истории подчиняется тому же правилу, что и чтение кода: оплачено названным
   фактом.
6. **Правило противоречия:** новый контракт сверяется с архивом по своим путям. Явное
   противоречие пункту старого контракта — эскалация владельцу: это смена решения, а не ремонт.
   Обычная правка, которая просто трогает тот же файл, не эскалируется. Построено 2026-11-26:
   читатель объявляется в `persona/validator.toml` и вызывается до оплаты исполнителя; он обязан
   назвать адрес в архиве и старый пункт дословно, а код проверяет, что и адрес, и пункт в архиве
   есть, — ссылка, которой нет, ничего не стоит. Задача при этом отказывается, а не чинится, и в
   записи и в `fasti` (`contract.contradiction`) остаётся фраза с обоими пунктами. Нет архива на
   этих путях — сравнения нет и денег нет; есть архив, а читатель не объявлен — запись говорит,
   что контракты не сравнивались: названный пропуск вместо тихого прохода.

   Живой прогон на коробке trajan (2026-11-26) нашёл две ошибки, обе исправлены. Первая: история
   рисуется строками `ожидаемое: …`, и читатель цитировал строку вместе с подписью — код считал
   цитату чужой, хотя пункт был на месте; подпись теперь снимается до сравнения, а сравнивается
   по-прежнему дословный пункт. Вторая: без годной цитаты в записи оставалась только фраза «ничего
   не вышло», и разобрать её было нечем; теперь запись хранит, что читатель сказал (обрезком), и
   цену вызова, а `contract_comparison` в записи называет историю, цитату и цену. Сравнение видно
   и в `status` (`contracts  on: …`), и в сводке `acta`.
7. **Построено 2026-11-26 вместе с первым читателем.** Архив без запроса — кладбище, поэтому
   вместе с записью единицы сделан `pantheon history`: список закрытых правок и выборка по путям
   (`--path src/app/**`), дифф — по требованию (`--diff <задача>/<метка>`), а не в общем ответе.
   Запись делает `_finish`: из той же записи, что ложится в `tabularium/`, а не из процесса,
   который эту запись создал. Хешируются определение проверки (из замороженной задачи) и её
   отчёт, у видимой — сама команда и её вывод; у отклонённых попыток — класс и хеш диффа, фраза
   «почему» — слова самой записи. Индекс по путям пересобирается из единиц при каждой записи:
   индекс, который может расходиться с единицами, — вторая правда об архиве. Дифф копируется в
   единицу, чтобы архив не зависел от каталога, который однажды почистят. Сбой записи не меняет
   вердикт и не молчит: событие `archive.failed` с причиной.

## ADR-046. Отказ приёмки: класс считается кодом, попыток две, трейс не скармливается обратно

**Принято 2026-11-26.** Приёмка может не пройти, и вопрос не в том, что делать с трейсом, а в том,
что он не должен становиться промптом: если отдать модели историю попыток, растут расход и дрейф.
Обрабатывается не трейс, а класс отказа — какие проверки разошлись. Это факт, его считает код.

1. **Классы.** Обе проверки упали — правка неполная: повтор ремонтнику с выводом видимой проверки.
   Видимая прошла, скрытая нет — правка подогнана под видимую или видимая слаба: повтор с пометкой
   «поведение не то», без текста скрытой; на повторе — класс «критерий слабый», и это работа
   репродьюсера. Скрытая прошла, видимая нет — сломана проверка, а не продукт: чинить проверку.
   Обе прошли, валидатор против — подмена требования: контракт уходит владельцу, повтора нет.
   Красная база не по нашей причине — чинить стенд, а не задачу.
2. **Две попытки** (пока). После второй неудачи задача возвращается с записью, не закрывается. Тот
   же класс дважды подряд — стоп раньше: повтор без прогресса не покупается. Потолок можно поднять
   до трёх — это число, а не принцип.
3. **Трейс — улика, не промпт.** В записи остаются контракт, карта, проверки, выводы, диффы
   попыток, класс и цена. Модель получает контракт, срез и вывод упавшей проверки — не историю
   разговоров.
4. **Класс считается по факту** — какие проверки упали и что сказал валидатор. Это
   детерминированная функция, поэтому остановка не зависит от настроения модели.

**Почему.** Репетиция трёх отчётов: в первом код-вердикт принял подмену формулировки; во втором
валидатор нашёл, что `resume` теряет уровень; в третьем расплывчатый отчёт дал отказ. Ни один
провал не был провалом исполнения — все были провалами критерия или формулировки.

**Следствие.** Приёмка трёхзначна: прошло, не прошло по правке, не прошло по критерию. Валидатор
не выносит вердикт — он называет контрпример; контрпример становится проверкой, и снова решает код.

**Следствие (2026-11-26, вторая попытка).** Повтор запускает сама коробка: `dispatch` (и очередь
`flow`) после повторяемого класса делает один `resume --retry` и возвращает уже вторую попытку, так
что отдельного «пойди и повтори» у владельца нет. Вторая попытка оплачивается из того же бюджета
задачи, поэтому отказ по деньгам или по потолку вызовов виден как остановка, а не как бесплатный
повтор. `steps`-движок и кампания второй попытки от `dispatch` не получают: у них свои циклы и свои
предохранители, и вторая попытка сверху означала бы начать их заново. Остановка пишется событием
`retry.stopped`: запись попытки уже зафиксирована, и дописывать её вывод значило бы менять запись
под её же вердиктом. Две попытки в одну секунду не теряют запись — метка сдвигается, и запись об
этом говорит; сводка второго захода получает время в имени, чтобы не затереть сводку первого.

## ADR-047. Проверка проверки: откатить кусок правки и посмотреть, заметит ли она

**Принято 2026-11-26.** Зелёная проверка говорит, что результат выглядит правильным, но не говорит,
что она вообще могла покраснеть. Репетиция это и показала: тест остался зелёным, когда из документа
убрали заголовок, который он якобы охранял. Нужен факт о самой проверке, а не о продукте.

1. **Метод — откат куска.** Берётся применённая правка; по очереди каждый кусок возвращается к
   прежнему виду в одноразовой копии дерева; та же проверка запускается снова. Покраснела —
   кусок замечен; осталась зелёной — проверка его не видит. Детерминированно, без модели.
2. **Кусок зависит от вида правки.** Новый файл — удалить его; удалённый файл — вернуть; блок
   текста (абзац, строка таблицы) — заменить прежним; значение конфига — вернуть прежнее значение.
   Переименование, форматирование и правки без смысловых кусков не тестируются.
3. **Откат обязан оставлять файл валидным.** Если откат ломает формат, проверка краснеет от
   поломки входа, а не от смысла: такой кусок пропускается с причиной, а не засчитывается как
   «замечено». Это главная ложь, которую метод обязан исключить.
4. **Код пока не тестируется.** Откат строки в коде обычно ломает синтаксис, и проверка падает от
   падения, а не от поведения. Нужен полноценный движок мутаций; до него кусок кода честно
   помечается «не тестируется», а не даёт ложную тревогу. YAML — по той же причине: в стандартной
   библиотеке нет парсера, а поддельный соврёт.
5. **Проверка должна быть зелёной на самой правке.** Красная на правке проверка не может заметить
   откат: прогон отказывается, а не выдаёт шум.
6. **Потолки — страховка от прожорливости:** не больше пяти кусков и 120 секунд на прогон; что не
   влезло, называется числом, а не теряется.
7. **Результат показывается, а не выносит вердикт.** В отчёте — замечено/слепо/пропущено с
   причиной; задача от этого не возвращается. Возвращать ли задачу по слепому куску и с каким
   классом — отдельное решение, когда будет видно, как часто это случается.

**Почему не готовый инструмент.** `pytest-gremlins` (MIT, 1.15.0) ломает только Python, ставится в
окружение проекта и на момент решения имеет статус alpha; наш случай — документы, конфиги и новые
файлы, где откат куска работает без парсера и без установки. Когда дело дойдёт до кода, инструмент
мутаций — кандидат; тогда откат строк останется для текста.

**Следствие.** `pantheon sensitivity <box> --task <файл> [--base <ref>]` читает правку из задачи,
работает в копиях и ничего не пишет; `dispatch` зовёт его сам и записывает отчёт рядом с вердиктом.
Первый живой прогон на изменении документации показал ровно то, ради чего он сделан:
проверка-`grep` заметила один кусок из пяти, остальные для неё не существуют.

Живой прогон задачи в коробке trajan нашёл ошибку: проект этой коробки — подкаталог репозитория, и
патч применялся в корне репозитория, где файла из правки нет. Теперь рабочее дерево по-прежнему
строится из репозитория, но правка и проверка говорят путями проекта внутри него; прогон на той же
правке дал «1 кусок, замечен».

**Проверка в диспетче.** Пункт 7 доведён: `dispatch` зовёт ту же репетицию, когда правка применена и
у задачи есть своя проверка, и кладёт отчёт в запись рядом с вердиктом. Это меньший прогон — три
куска и 90 с на весь шаг, потому что вердикт уже оплачен и репетиция не может его пережить; проверка,
слишком медленная или уже красная, называется непосчитанной, а не выдаёт шум. Вердикт, состояние и
код выхода от репетиции не зависят: слепой кусок показывается заметкой записи, но задачу не
возвращает. Возвращать — отдельное решение, и оно по-прежнему за владельцем.

## ADR-048. Движок мутаций: аудит проверок по триггеру, а не гейт

**Принято 2026-11-26.** ADR-047 п.4 честно оставляет код без репетиции: откат строки ломает
синтаксис, и проверка краснеет от поломки, а не от смысла. Закрыть это может только движок
мутаций, но он дорог: цена ≈ мутанты × время набора. Гонять его на каждой правке — значит платить
за аудит проверок в каждом багфиксе и тормозить поток; отказывать правке по выжившему мутанту —
смешивать «код неверен» с «проверка слаба».

1. **Мутации — аудит проверок, не гейт.** Задача никогда не ждёт мутаций, и выживший мутант не
   возвращает задачу и не меняет вердикт. В записи — число и адрес мутанта, не приговор.
2. **Триггеры, по убыванию ценности:** (а) после ложного `pass` или утекшего бага — аудит
   тронутого модуля один раз, это прямое доказательство слепоты проверки; (б) когда написана
   новая проверка на дефект (`repro`) — один прогон «убивает ли она мутантов вокруг правки»;
   (в) периодический отчёт — раз в месяц, только чтение, динамика по модулям; (г) перед релизом
   или крупным разворотом — только критические пути.
3. **Объём — кусок правки или один модуль.** Никогда весь репозиторий: мутанты по изменённым
   строкам, потолок по времени и числу; что не влезло, называется числом, а не теряется.
4. **Эквивалентный мутант — кандидат, а не дыра.** Выживание записывается с адресом и строкой;
   человек или тест решает, дыра это или эквивалент. Автоматического «вернуть задачу» нет.
5. **Инструмент — сменный.** Первый — Python (`pytest-gremlins`, MIT, alpha); интеграция на
   уровне отчёта sensitivities и записей, не зависимостью среды: harness остаётся на стандартной
   библиотеке.
6. **Пока не построено.** До движка код честно называется «не тестируется» (ADR-047 п.4);
   решение фиксирует сценарии, чтобы мутации не гонялись в каждом прогоне и не выдавались за
   вердикт.

## ADR-049. Пакет контекста: одна строка последствия вместо указателей

**Принято 2026-11-26.** D21 велел собирать контекст кодом и класть перед моделью прошлые задачи по
путям с причиной и **указателями**: адрес записи и путь её файла, «модель открывает полную запись,
только если это решает работу». Замер (`pilot/context-block/`) показал, что вторая половина этого
правила не выполняется: за шесть боевых прогонов ни один не открыл ни одной записи, хотя каталог
смонтирован и читается. При этом указатели не были пустым местом для модели: она их читала и
ссылалась на них в рассуждении. А ответ с полным списком и без блока вовсе совпал побайтно — значит
список не менял работу, а стоил 2 550 символов (~640 токенов) в каждом ходе, пересылаемых на каждом
вызове модели.

1. **Блок — одна строка последствия.** Сколько записанных изменений касается объявленных путей,
   какое из них последнее (задача, вердикт, тема) и что отмена записанного решения — дело владельца:
   «если задача сама того не просит — не отменяй». Строка отвечает на вопрос «что здесь уже решено»,
   а не перечисляет, где это лежит.
2. **Инвентарь остаётся в записи, не в промпте.** Адреса, причины отбора («touches src/click/core.py»),
   счёт вытесненных и нечитаемых записей живут в JSON пакета и в `pantheon records`; человеку они
   нужны, модели — нет.
3. **Потолок — 600 символов и одна строка.** Длинная тема режется по слову, а не тащится целиком;
   если блок когда-нибудь снова станет списком, это отдельное решение с отдельным замером.
4. **Строка напоминает, а не запирает.** Отказать задаче она не может: отмена записанного решения
   остаётся у валидатора противоречия (ADR-045 п.6) и у владельца, а исполнитель — не вторые ворота.
   Отказ исполнителя на задачу, которую владелец отправил, был бы гейтом не на том слое.
5. **Что куплено и что нет.** Куплено: напоминание в шесть раз дешевле (437 символов против 2 550,
   ~110 токенов против 640; сами токены — около 0,001¢ за ход). Не куплено: изменённый ответ — на
   задаче-отмене правка та же, что без блока. Для закрытых задач строка дублирует сообщение коммита
   (номер задачи, вердикт, тема), которое модель читает сама; уникальна она для истории без коммита —
   остановленных и возвращённых попыток.
6. **Триггер пересмотра.** Если у коробки появятся задачи, где решение принимается только по
   незакоммиченной истории, или если модель начнёт открывать записи сама, — блок пересматривается
   новым замером, а не догадкой.

## ADR-050. Потолок памяти коробки: 1 ГБ, потому что 512 МБ убивали ход

**Принято 2026-11-26.** `MEMORY_LIMIT = "512m"` ставился как страховка: контейнер агента не должен
съесть хост. Замер честного A/B (`pilot/bare-honest/`) показал, что страховка била не по хосту, а по
самой работе: шлюз и CLI агента занимают ~370 МБ анонимной памяти, и ядро убивало `hermes` по OOM
через 20 с после старта хода. Два первых хода умерли ровно с двумя OOM в журнале ядра (20:22:48 и
20:23:52) и без единой правки. Тем же «Gateway disconnected; turn outcome is unknown» кончились все
шесть ходов голого в серии и один вызов коробки — это был тот же OOM, а не «обрыв шлюза».

1. **Потолок 1 ГБ, а не «снять».** Хост общий (12 ГБ, рядом демо), потолок остаётся стражем. 1 ГБ —
   с запасом: анонимная память хода ~370 МБ, остальное занимает страничный кэш, который ядро отдаёт
   под давлением. За пять ходов при 1 ГБ — ноль OOM.
2. **Страж ниже собственного аппетита агента — не страж, а поломка.** Граница, в которую агент
   упирается на 20-й секунде, защищает хост от работы, а не работу от хоста: вместо отказа на входе
   она убивает ход, теряет счёт и оставляет «неизвестный исход».
3. **Цена ошибки названа в деньгах.** Два убитых хода — 0,62¢ и два пробных вызова — 0,01¢; в серии
   тот же OOM стоил 16¢ фантомных зарядов (сторож подставлял потолок вместо фактической цены;
   лечение — `fe7364d`).
4. **Что не решено.** `less` в образе нет: набор внутри контейнера красен на 24 тестах пагинатора
   при любом коде. Коробку это не задевает — её ворота гоняют набор на хосте, — а любой замер внутри
   контейнера задевает. На этот раз `less` поставлен в живой контейнер и при пересоздании исчезнет.
5. **Триггер пересмотра.** Если анонимная память хода подойдёт к 1 ГБ или хост начнёт делить коробку
   с другими тяжёлыми процессами, потолок пересчитывается по `memory.peak` и `memory.stat`, а не на
   глаз.

## ADR-051. Самопроверка в контейнере: `up` ставит инструменты, карточка называет команду

**Принято 2026-11-26.** До этого дня исполнитель не мог проверить себя, и это было решением, а не
недосмотром: проект смонтирован только на чтение, venv проекта собран под 3.12 при системном 3.13 в
контейнере, а промпт прямо запрещал запускать набор — «этого окружения у тебя нет». Честный A/B
показал цену этого решения: агент, у которого проверка работает, дал 5/5 зелёного за 0,26–0,81¢ на
задачу, тогда как коробка платит в среднем 1,23¢ и получает красные первые ответы, потому что
узнаёт о поломке от ворот, а не от себя.

1. **`up` ставит то, без чего проверка красна по причине среды.** `BOX_PACKAGES = ("less",)`:
   в образе нет `less`, и 24 теста пагинатора в проекте-примере красны при любой правке. Установка
   идемпотентна (сначала `command -v`, потом `apt-get`), а неудача — ошибка `up`, а не заметка:
   среда, собранная наполовину, опаснее несобранной.
2. **Самопроверка разрешена, ворота остаются судьёй.** Агент копирует проект в `/opt/data/work/` и
   гоняет команду, названную карточкой; ответ он всё равно отдаёт дифом, а вердикт выносит прогон
   коробки. Самопроверка — способ не тратить комнату вызова на заведомо красное, а не вторая приёмка.
3. **Карточка называет работающую команду, а не намерение.** `.venv` проекта собран под 3.12, а
   системный интерпретатор в контейнере — 3.13, поэтому `.venv/bin/python -m pytest` не видит pytest,
   хотя он установлен; рабочая форма — `PYTHONPATH=src:.venv/lib/python3.12/site-packages
   /usr/bin/python3 -m pytest -q`. Карточка, называющая нерабочую команду, хуже отсутствия карточки.
4. **Замер сделан в тот же день, на двух задачах серии.** С самопроверкой: задача 1 (та, где раньше
   первый ответ был красный и ворота отказывали) — **1 попытка, 1,47¢, 117 с** вместо 2 попыток,
   2,58¢ и 186 с; задача 2 — **0,43¢ и 52 с** вместо 0,74¢ и 56 с. Обе зелёные с первого ответа,
   verdict `pass`. Итого на этих двух задачах 3,32¢ → 1,90¢, время 242 с → 170 с. Это сигнал, а не
   доказательство: две задачи, один прогон, и часть разницы могла дать сама карточка с командой
   (в старом прогоне её не было).
5. **Триггер пересмотра.** Если ходы станут заметно длиннее и дороже (агент гоняет набор ради
   любопытства), запрет возвращается в промпт, а список пакетов сокращается до нужного.


## ADR-052. Достройка на живом проекте: спецификация до работы, а у теста — названная поломка

**Принято 2026-11-27.** Первая задача не на демо-проекте, а на DocFlow: не фича, а тесты — «пока
тесты», но сценарий тот же, что у достройки (D44/ADR-043 п.3), и по дороге он дал критерий для
целого класса задач. Задача: `crm.py` собирает то, что уходит в CRM (заголовок документа и
комментарий к сделке), и тестов у этих двух функций ноль; покрытие файла 56%.

1. **Достройка идёт тем же путём, что и фича.** Задача `kind = "feature"`, `repro` — это
   спецификация, написанная до работы и красная потому, что поведения (или файла теста) ещё нет;
   владелец принимает спецификацию словами до запуска; вердикт — `repro` плюс оба набора проекта
   (политика DocFlow: набор продукта с гейтом покрытия и набор ассистента), коммит — в ветке.
   Preflight остаётся тем же и уже окупился: он поймал сломанную спецификацию (`SyntaxError` в
   хвосте) до оплаты модели — это и есть «красна не по той причине», которую видно в хвосте.
2. **Критерий задачи «написать тест» — тест, который краснеет от названной поломки.** `repro`:
   (а) требует названный файл теста; (б) гоняет его на чистой копии `git archive HEAD` плюс этот
   файл из рабочего дерева — должен быть зелёным; (в) вносит в копию одну названную поломку
   (здесь — из комментария убрана строка `Phone:`) и требует красного. Копия, а не рабочее дерево:
   продукт не мутируется ни на секунду. Больше проверка не обещает: она доказывает, что тест
   замечает одну названную поломку, а не что он покрывает всё.
3. **Почему не «файл существует и зелёный».** Зелёный тест на текущем коде говорит «ничего не
   сломалось», а не «тест что-то проверяет»: `assert True` прошёл бы. Названная поломка —
   механическая, и её замечает код, а не читатель отчёта. Это тот же ход, что `repro` у ремонта,
   только поломку вносит не дефект, а проверка.
4. **Самопроверка в контейнере на DocFlow невозможна.** В образе python 3.13/3.14, venv проекта —
   3.12 с собранными расширениями (flask, pydantic), pytest в образе нет; запуск набора там падает
   по причине среды. Карточка проекта говорит это прямо, а общий промпт исправлен: проверять себя
   можно только когда карточка называет рабочую команду, иначе — сразу ответ. D52/ADR-051 остаётся
   для проектов, где команда работает.
5. **Живой прогон.** Первая попытка: агент копировал проект и искал pytest в контейнере, потолок
   вызова 300 с убил ход, цена не отчиталась, и задача закрылась потолком 8¢ — вторая попытка была
   остановлена бюджетом, а не делом. Наследник (в файле — `parent` и `why`) поднял потолок вызова до
   600 с, снял видимую проверку (в контейнере её нечем гонять) и назвал причину. Второй прогон:
   **89,5 с, 0,55¢** (176 616 входных токенов, 166 144 из кэша), verify 143,6 с, 3 из 3 проверок,
   `crm.py` 56% → 87%, покрытие проекта 74,31% → 75,25%, коммит `6f3fcef` в ветке
   `pantheon/crm-tests`. Спецификация совпала с ответом: восемь тестов, все поля, валюта, маршрут,
   пустые поля.
6. **Дефект коробки, найденный этим прогоном.** `up` сеял `config.yaml` через
   `docker compose run -u <uid>`, а образ отказывается стартовать с произвольным UID: свежая
   коробка оставалась без конфига и не поднималась, `up` печатал предупреждение и выходил.
   Исправлено: сев без `-u`, владение задают `HERMES_UID`/`HERMES_GID` из compose; тест требует,
   чтобы в команде сева не было `-u`, а в compose были оба UID.

**Следствие.** Ветка `pantheon/crm-tests` — не main: слияние и пуш остаются словом владельца.
Задача «тест» теперь стоит один вызов и ~0,5¢ на этом проекте, а её вердикт не зависит от того,
как красиво тест назван. Ограничение, которое надо помнить: названная поломка — одна; тест может
быть зелёным на ней и слепым к другому поведению, и это видно из записи, а не скрыто.
