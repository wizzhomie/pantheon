# 06. Risk Analysis

## Главный риск

**Август — самая недетерминированная часть системы, и на нём же держится больше всего.** Он решает,
какие контуры звать, формулирует задачи и обновляет состояние. Если он ошибается, ошибка тихая: нет
падения, нет ошибки в логах — просто задача ушла по неполному процессу.

Лечение, заложенное в архитектуру: маршрутизация — таблица по объявленным полям (ADR-007); план виден в
задаче и оспаривается человеком; отсутствие контура в прогоне всегда видимое состояние, а не пропуск
(§03 «Деградация»). Август может сделать процесс **строже**, но не может молча сделать его слабее.

## Реестр рисков

| Риск | Механизм | Ранний признак | Что делаем |
|---|---|---|---|
| Август обходит контракт | у него есть родной shell или запись | попытка записать файл вне `pantheon run` | профиль без shell (ADR-004), проверка тестом на старте коробки |
| Caesar становится фреймворком | начинает вызывать Aurelius/Trajan, планировать | в контракте появляются поля «следующий шаг» | запрет на планирование внутри Caesar; ревью при каждом расширении |
| Aurelius дублирует Trajan | сам выносит «соответствует архитектуре» | два вердикта по одному изменению | Aurelius даёт правила, вердикт — только Trajan |
| Два источника правды | копия требований в реестре | правка в файле не доехала до памяти | реестр хранит только ссылки на id |
| Память гниёт | записи без происхождения | на вопрос «почему так» есть текст, но нет доказательства | запись без ссылки — мнение и помечается (`unverified`) |
| Обновление снесло коробки | `latest` вместо тега | тег в `castrum.toml` содержит `latest` | запрещено ADR-010 |
| Контейнеры в память не влезают | каждая коробка держит процесс | swap/давление памяти на хосте | поднимать по требованию, гасить простаивающие |
| Стоимость на коробку | Август и ревью в цикле | бюджет задачи выбирается за одну попытку | бюджеты в `castrum.toml` и в контракте; событие при превышении |
| Читатель судит обрезанное изменение | промпт режется на 120 КБ, дифф — на 200 КБ; «находок нет» неотличимо от «не видел» | отчёт не говорит, сколько файлов попало в чтение | D31/ADR-030: `Files shown`, `truncated`, в пробелах — «видел N из M файлов» |
| Кэш ревью путает разные изменения | после обрезки два разных диффа дают одинаковый промпт | `cached: true` на новом изменении | ключ кэша включает отпечаток диффа, а не только промпт |
| Потолок счёта не останавливает вызов | цена узнаётся после ответа модели | запись с ценой выше потолка | цена и перерасход пишутся как факт и как пробел; упреждающий отказ — открыт |
| Зависимость от внутренностей Hermes | плагины/скиллы/ACL меняются между версиями | апдейт образа ломает коробку | фиксация тега, апгрейд как отдельная задача с прогоном приёмки |
| Личный Hermes становится зависимостью | обратный запрос из коробки | коробка не работает без ассистента | односторонний acta (ADR-011) |
| Демонстративность | всё отлично на своём идеальном примере | на чужом репозитории ноль находок | оценка на сторонних репозиториях (§09) |
| Один сопровождающий | четыре контура плюс коробка | отставание одного компонента на месяц | MVP-срез, отказ от параллельной разработки контуров |
| Портфолио-история размывается | оркестратор — сторонний продукт | «а что вы написали сами?» | честная формулировка: расширение harness своим контуром проверки; вклад виден по ADR, тестам, оценке |
| Скрытая сложность «настоящей коробки» | фантазия про контейнер-посылку | попытка сделать это до MVP | в MVP проект монтируется (ADR-002) |
| Быстрый набор пропускает нужную проверку | набор выбран ниже риска правки | ложный `pass` там, где полный набор покраснел бы | нижняя граница по путям, долг проверок, полный набор на контрольной точке (D32/ADR-031) |
| Рельсы обходятся прямыми правками | человек правит файлы мимо коробки | коммиты без `Pantheon-Task` в сообщении | записывать как нарушение или явно разрешить исключения (открытый вопрос в `docs/12-rails.md`) |
| Вопросы выматывают владельца | онбординг и ревизии спрашивают слишком часто | ответы «на усмотрение» подряд, вопросы пропускаются | умолчания у каждого вопроса, спрашивать при онбординге и ревизии, не на каждой задаче (D35/ADR-034) |

## Риски, которые легко недооценить

1. **Соблазн «умной маршрутизации».** Как только Август начнёт решать, нужна ли архитектурная проверка,
   по своему усмотрению, появится класс задач, которые проходят без неё, и никто не заметит.
2. **Утечка контекста между коробками.** Два экземпляра Hermes с общей моделью памяти начнут
   пересказывать друг другу чужие проекты. Держим раздельные тома и не даём коробкам общего хранилища.
3. **Ложная зрелость.** Красивые отчёты и зелёные галочки при отсутствии находок на реальных задачах.
   Признак: количество вердиктов растёт, количество найденных проблем — нет.
4. **Правка модели Aurelius под ответ.** Соблазн «подкрутить» архитектурную модель, чтобы проверка не
   падала, — то же самое, что править тест под код. Лечится правилом: модели и правила меняются только
   вместе с обоснованием в ADR.

## Когда останавливаемся

Три условия, при которых честнее остановиться и пересмотреть решение:

- на пяти сторонних репозиториях Trajan не находит ничего, что человек подтвердил бы как проблему;
- Август стабильно выбирает процесс хуже, чем таблица по объявленным полям (то есть его «понимание»
  вредит);
- стоимость одной задачи в коробке превышает ручную работу над ней без заметного выигрыша в качестве.

Первое и второе проверяются в [09-evaluation.md](09-evaluation.md), третье — в каждом прогоне как число.
