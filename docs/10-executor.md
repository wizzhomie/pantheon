# 10. Исполнитель: команда, которая производит изменение

Изменение производит **объявленная команда** — исполнитель: задача на stdin, патч и счёт на stdout.
Его исполнение бывает разным, и harness этого не различает: DeepSeek по API, `claude -p` по подписке,
ваш собственный скрипт или — с 2026-11-24 — агент коробки внутри контейнера
(`bin/pantheon-executor-container`). Во всех случаях остальное одно: патч проходит через ворота
Caesar, проверку запускает Trajan, запись ведёт Augustus.

Смысл в том, что harness не знает, кто именно ответил: он знает только формат ответа и что с
ответом делать.

Ответов может быть несколько. С 2026-11-25 у коробки два **движка**, и оба говорят на одном
протоколе: `one-shot` спрашивает один раз и живёт с ответом, `steps` применяет ответ, гоняет
видимую проверку задачи и спрашивает снова — до потолка вызовов, пока не кончится бюджет или пока
ответ не перестанет двигать дерево. Движок выбирает коробка по виду задачи, как и модель, и это
решение записывается.

## Что объявляет коробка

Файл `persona/executor.toml` в коробке:

```toml
schema_version = 1
command = "/home/ubuntu/pantheon/bin/pantheon-executor"
model = "deepseek-flash"   # необязательно: имя по умолчанию
max_seconds = 300
max_cents = 5
max_output_tokens = 32768  # необязательно: потолок выдачи провайдера по умолчанию
max_steps = 6              # необязательно: потолок вызовов на задачу
engine = "one-shot"        # необязательно: движок для видов без своей записи

# Модель по виду задачи: ключ — `kind` из файла задачи. Тариф (долларов за миллион
# токенов) объявляет коробка, иначе цена второго вида считалась бы по чужому прайсу.
# `max_output_tokens` — потолок самой модели, если он ниже общего.
[models.docs]
model = "deepseek-chat"
price_in = 0.15
price_out = 0.60
max_output_tokens = 32768

# Форма изменения объявляет только масштаб правки. Комнату вызова коробка считает из
# денег задачи, а не из формы: одна строка может требовать больше размышления, чем
# перепечатка файла, и на этом endpoint размышление входит в те же токены.
[shapes.patch]
max_changed_lines = 40
max_files = 1

# Граница исполнения: после неё one-shot не запускается. L1 — shape patch, без self_check,
# не больше файлов/строк ниже; L2 — есть self_check и потолок вызовов; L3 — всё остальное,
# и это отказ `needs-agent`, пока агента нет. Без таблицы граница не enforced (legacy).
[execution]
one_shot_max_files = 2
one_shot_max_changed_lines = 30
steps_max_files = 3
steps_max_changed_lines = 100

# Движок по виду задачи: ключ — `kind` из файла задачи. Вид без записи получает `engine`.
[engines]
bugfix = "steps"
```

Нет файла — нет исполнителя: задача тогда должна нести свой патч, и запись так и говорит.

Бюджет задачи может **уменьшить** лимиты коробки, но не увеличить: потолок задаёт коробка.
`max_cents` задачи — это **сумма на всю задачу**, а не квота на попытку (ADR-037): harness
складывает цену уже сделанных вызовов по записям, и следующий вызов получает только остаток.
`max_steps` задачи и коробки тоже складываются в минимум: задача может попросить меньше вызовов,
чем разрешила коробка, но не больше.

**Модель по виду задачи.** Вид берётся из задачи, а не угадывается по тексту: `[models.<вид>]`
называет модель и, если нужно, её тариф. Выбор делает harness до вызова: есть запись для вида —
она, иначе `model`; выбранная модель уходит в запрос полем `model`, тариф — в окружение команды
(`PANTHEON_MODEL_PRICE_IN`/`PANTHEON_MODEL_PRICE_OUT`), а решение пишется в `proposal.json`
полем `model_choice` и в событие `task.executed` тем же полем. Если тариф не объявлен, окружение
не переопределяется и цена остаётся за командой. Одна половина тарифа без второй — отказ профиля:
половина цены не цена.

**Движок по виду задачи.** Вид решает не только модель, но и режим: `[engines.<вид>]` называет
`one-shot` или `steps`, вид без записи получает `engine` (по умолчанию `one-shot`). Решение
пишется в `proposal.json` полями `engine` и `engine_choice` и в запись — полем `engine`, так что
«почему эта задача шла шагами» — факт, а не догадка по числу попыток. Задача говорит, за сколько
вызовов готова платить (`max_steps`), коробка — сколько верёвки получает этот вид работы.

**Граница one-shot.** Если коробка объявила `[execution]`, до вызова считается уровень:
`shape = "patch"`, без `self_check`, в пределах `one_shot_max_files`/`one_shot_max_changed_lines`
— L1, один вызов. Есть `self_check`, в пределах `steps_max_files`/`steps_max_changed_lines` и есть
потолок вызовов — L2, `steps`. Всё остальное — L3, и это отказ `needs-agent`: коробка не делает
вид, что один вызов справится. Явная таблица `[engines]` может сделать исполнение тяжелее
(`steps` на L1 разрешён), но не легче: `one-shot` на L2 повышается до `steps`, L3 не запускается.
`explain` печатает уровень и причину до вызова; `dispatch --json` пишет `level` и `route`; в
`proposal.json` остаются `engine` и `engine_choice`. Без `[execution]` граница не enforced, и
`explain` называет это пробелом.

Движку `steps` нужен **потолок вызовов**: `max_steps` задачи или коробки. Без него задача
отказывается до первого вызова — цикл без потолка не начинается. С `one-shot` потолок остаётся
тем, чем был: сколько раз задачу вообще можно спросить (повторы и продолжения).

`command` — не «модель», а обычная команда. Её можно заменить на любую другую, которая говорит
на этом протоколе.

## Запрос: что команда получает

Задача приходит JSON-объектом на stdin и одновременно лежит в `tabularium/<task>/proposal-<n>/request.json`:

```json
{
  "schema_version": 1,
  "attempt": 1,
  "turn": 1,
  "turns": [],
  "task": {"id": "t-1", "goal": "…", "kind": "bugfix", "paths": ["src/**"],
           "expected": "…", "forbidden": [], "budget": {"max_cents": 5},
           "max_steps": 6},
  "project": {"path": "/home/ubuntu/pantheon/trajan"},
  "box": {"name": "trajan", "root": "/home/ubuntu/pantheon/castra/trajan"},
  "limits": {"max_seconds": 300, "max_cents": 5, "max_read_chars": null,
             "max_answer_tokens": 4096, "max_steps": 6},
  "record": {"directory": "/home/ubuntu/pantheon/castra/trajan/tabularium/t-1/proposal-1"},
  "model": "deepseek-flash",
  "engine": "steps",
  "engine_choice": "steps, declared for kind bugfix",
  "context": {"…": "пакет контекста, если коробка его собрала"},
  "previous": null
}
```

`limits.max_answer_tokens` — комната, которую коробка вычислила из остатка бюджета задачи:
остаток минус резерв (на промпт и следующий шаг) переводится в токены по цене выхода модели и
ограничивается потолком провайдера (`max_output_tokens`). Форма изменения комнату не задаёт: она
называет только масштаб правки (`max_changed_lines`, `max_files`). Одна и та же строка кода может
требовать больше размышления, чем механическая перепечатка файла, а на этом endpoint размышление
входит в те же токены, что и ответ.

Если в остатке нет денег на полезный вызов, коробка не спрашивает: запись `insufficient-budget`
называет, сколько осталось и сколько нужно. `null` — только у прямого вызова без коробки: тогда
действует `PANTHEON_MODEL_MAX_TOKENS`.

Форма названа и в самом `task`, и словами в промпте: модель вправе ответить `ERROR: <что нужно>`,
если правка не влезает в объявленный масштаб, и коробка записывает это как неверную оценку
размера. `max_changed_lines` и `max_files` — граница ответа: ответ сверх них называется «не в
форме», не применяется, а оба числа (что пришло и что позволено) уходят в запись и в факты повтора.

`limits.max_cents` — не объявленный бюджет задачи, а то, что осталось на **этот** вызов: harness
вычитает из бюджета то, что уже заплачено по записям задачи. Первый вызов видит весь бюджет,
второй — остаток, и `proposal.json` этого вызова называет потолок, с которым он пришёл. Разница
между `task.budget` и `limits` — не дефект, а факт: задача объявила одно, вызову досталось другое.

**Как считается комната.** Деньги — бюджет, комната — производная. Из остатка вычитается резерв:
на шагах — четверть (следующий шаг и его промпт), у `one-shot` — десятая часть; пол резерва 0,5
цента, потому что промпт оплачивается до ответа. Остаток переводится в токены по цене выхода
модели и обрезается потолком провайдера. Если цена модели не объявлена, комната — потолок
провайдера, и запись говорит, что стоимость не была ограничена до вызова. Если на полезный вызов
денег не хватает (меньше 1 024 токенов), коробка не спрашивает: `insufficient-budget` с числами.

Комната — это **потолок, а не план**: короткий ответ стоит дешевле, и неиспользованное место
ничего не стоит. Обрыв на комнате означает, что деньги задачи купили ровно столько и модель
истратила это на размышление; повтор в том же бюджете дал бы **меньше** места (остаток — это
резерв, а не новая комната), поэтому коробка не делает вид, что повторяет с большей комнатой:
она записывает `finish_reason`, сколько токенов ушло на размышление, и передаёт решение о бюджете
владельцу (`resume` с поднятым `max_cents` — уже новый бюджет, а не трюк).

`limits.max_read_chars` — потолок чтения на задачу: если задача объявила `max_read_chars` в
`[budget]`, команда обязана не читать больше, а всё, что не влезло, назвать в ответе. `null` —
потолок не объявлен, действует собственный предел команды.

`turn` — номер вызова в задаче (у `one-shot` всегда 1), `turns` — короткая история прошлых шагов
движка `steps`: что ворота сделали с каждым ответом и что сказала видимая проверка. Это факты из
записей коробки, а не пересказ: применённый шаг называет `check` (статус, код выхода, хвост),
отклонённый — `refused` и причину, ответ без изменения — `failed`. Видимую проверку (`self_check`)
модель читает, скрытую (`repro`) — нет; в `turns` попадает только видимая. `limits.max_steps` —
потолок, который действует на деле (минимум из задачи и коробки).

`previous` — не `null` только у повтора: это факты прошлой попытки (вердикт, проваленные проверки,
находки), собранные кодом из записи; исполнитель обязан на них ответить, а не повторить задачу
ещё раз. Одиночная задача (`resume --retry`) получает те же факты, что и шаг кампании, и её черновик
перед повтором откатывается — исполнитель читает файлы с диска и иначе прочитал бы отклонённое как
проект (2026-11-25).

`repro` — команда, которой задача проверяется, — в `task` **не передаётся**: модель видит цель,
объём и слова `expected`, но не сам вход. Зато передаётся `self_check` — видимая проверка (D36,
ADR-035): коробка прогоняет её после изменения и пишет результат рядом с вердиктом, но вердикт
выносит только `repro`. Повтор получает слова видимой проверки, а не скрытой: иначе вторая проверка
стала бы первой, и подгонка вернулась бы на второй попытке. Расхождение («видимая зелёная, скрытая
нет») записывается в `self_check`, в строку `own check` отчёта и отдельной нотой.

Команда запускается в каталоге проекта и вправе проект **читать**.

## Ответ: что команда возвращает

JSON-объект на stdout, ничего больше. Ключи:

| Ключ | Обязателен | Что значит |
|---|---|---|
| `patch` | один из двух | унифицированный диф текстом |
| `patch_file` | один из двух | путь к дифу; относительный считается от `record.directory` |
| `usage` | нет | `prompt_tokens`, `completion_tokens`, `cost_cents` — что потрачено |
| `model` | нет | имя модели, как его назвал поставщик |
| `notes` | нет | список строк, которые попадут в запись |
| `reading` | нет | что команда прочитала: `files`, `chars`, `tokens_estimate`, `cap_chars`, `declared_chars`, `left_out` (список строк) |
| `duration_ms` | нет | сколько заняло по мнению команды |
| `truncated` | нет | `true` — ответ оборван потолком токенов; такой диф не применяется |
| `done` | нет | `true` — работа закончена, диффа нет; у `steps` это конец цикла, вердикт всё равно считает скрытая проверка. `done` и патч вместе — дефект протокола |
| `error` | нет | «я не смог»; это записывается как отказ, а не как пустой патч |

Неизвестный ключ — дефект протокола: ответ считается неудачным, а не «почти правильным».
Пустой ответ — тоже неудача: «ничего не вернул» не равно «изменение не нужно».

## Цикл шагов

`steps` — тот же протокол и те же ворота, но контроллер спрашивает несколько раз. Один шаг — один
вызов; применённый ответ — попытка (нумерация `tabularium/<id>/<n>/`); рядом с ней коробка пишет
результат видимой проверки (`self-check.json`) и короткую запись шага
(`proposal-<n>/step.json`). Следующий запрос получает эти факты в `turns`, а не рассказ о них.

Что видит модель на шаге N: задачу, пакет контекста, список прошлых шагов и хвост последней
видимой проверки. Чего не видит: `repro` и данные, на которых он гоняется. Дерево к этому моменту
уже содержит применённые шаги — модель читает проект как он есть и правит свой прошлый шаг.

Цикл заканчивается только по фактам из записей коробки:

| Условие | Когда | Что записано |
|---|---|---|
| ответ без патча, `done` или `ERROR:` | после ответа | шаг, затем `verify` по накопленному дереву |
| тот же дифф, что уже в дереве | до ворот | шаг `repeated`, цикл стоит |
| исчерпаны `max_steps` | до вызова | `stop_reason`, дальше `verify` |
| исчерпан бюджет задачи | до вызова | `stop_reason`, дальше `verify` |
| две применённые попытки подряд провалили видимую проверку одними словами | до вызова | `stop_reason`, дальше `verify` |
| видимая проверка прошла | после шага | цикл стоит; вердикт считает `repro` |
| ворота отказали | после ответа | шаг `refused`; следующий шаг читает отказ как факт |
| команда написала в проект сама | после ответа | `unapproved-write`, задача возвращается без проверки |

Остановка в цикле — не вердикт: если хотя бы один шаг уже применён, `verify` всё равно считается по
накопленному дереву, а `stop_reason` остаётся в записи. `state = stopped` и код 2 — только когда
платить не за что и менять нечего: до первого применённого шага. Коммит после `pass` собирается из
**всех** применённых шагов по порядку — это то же дерево, которое проверяли, а не только последний
дифф.

Продолжение: `pantheon resume` без `--retry` продолжает незаконченный цикл по записям (последний шаг
применён и видимая проверка провалилась, или ворота отказали), а не проверяет половину дерева как
готовую. `resume --retry` сначала откатывает **все** применённые шаги последнего прогона (последний
первым) и пишет их номера в `reverted.json`: новый прогон не должен коммитить откатанное.
Незаконченный вызов (ответ записан, ворота не видели) продолжение не переспрашивает — он
применяется, потому что уже оплачен.

## Что harness делает с ответом

0. **Проверяет, есть ли ещё право на вызов.** До запроса считаются сделанные вызовы (по каталогам
   `proposal-<n>`, кроме `billing_status = not_billed`), их цена (по `proposal.json`; вызов без
   названной цены считается по потолку коробки) и цена чтения из записей. Если задача исчерпала
   `max_cents` или `max_steps` — вызова нет, запись получает `stop_reason` и код 2. Так же
   останавливает повтор, который две попытки подряд провалил видимую проверку одними и теми же
   словами: это не вердикт, а отказ платить за ответ, который не двигается.
1. **Ограничивает время.** Не уложилась в `max_seconds` — процесс останавливается, попытка
   записывается как неудачная.
2. **Проверяет, что команда не писала сама.** До и после вызова снимается `git status` и `HEAD`:
   если дерево изменилось, это `unapproved-write` — изменение не применяется, задача возвращается.
   Команда предлагает, а не пишет.
3. **Проверяет цену.** Если ответ говорит про `cost_cents` больше разрешённого — изменение
   записывается, но не применяется (`over-budget`).
4. **Отказывает оборванному ответу.** Если ответ помечен `truncated` (модель упёрлась в комнату,
   которую купили деньги задачи), диф записывается с ценой, но **не применяется** (`incomplete`):
   диф, оборванный на комнате, может примениться и оставить набор зелёным, а половины правки в нём
   не будет. Запись называет `finish_reason`, комнату и `reasoning_tokens`: «думала 8 192 из
   8 192» — факт, а не догадка. Пустой ответ по длине — тот же `truncated`, а не «модель молчит».
5. **Отдаёт патч Caesar.** Тот же контракт, те же ворота, тот же отказ по путям.
6. **Зовёт Trajan** после применения — как и раньше.
7. **Записывает чтение.** Если ответ назвал `reading`, запись, `pantheon dispatch` и `pantheon
   status` печатают, сколько файлов и символов попало в запрос, оценку токенов и что осталось за
   потолком. Не назвала — запись говорит «not reported», а не рисует ноль.

Каждый вызов оставляет каталог `tabularium/<task>/proposal-<n>/`: `request.json`, `stdout.txt`,
`stderr.txt`, `change.diff`, `proposal.json` (со статусом, ценой и токенами).

## Где видна стоимость

Критерий приёмки MVP — «стоимость задачи записана». Она записана в трёх местах:

- **событие** в `fasti/<дата>.jsonl` типа `task.executed` с полями `model`, `prompt_tokens`,
  `completion_tokens`, `cost_cents`, `seconds`;
- **запись** `dispatch-*.json`, блок `executor`, и `proposal.json`;
- **сводка** в `acta/`, раздел `## cost`: деньги, токены, модель, время и бюджет задачи.

Чтение — отдельная строка `reading` в `dispatch-*.json`, в `proposal.json` и в выводе `pantheon
dispatch`: файлы, символы, оценка токенов, объявленный потолок и всё, что осталось за ним. Три
правила записи:

- **Токены не выдумываются.** Не сообщила команда — в записи стоит «tokens not reported», а не 0.
  Если провайдер назвал `reasoning_tokens`, запись отделяет размышление от ответа: «17 402
  thinking, 326 answer» — это факт, по которому видно, куда ушла комната.
- **Деньги не выдумываются.** Нет цены — «cost not reported» (а не «бесплатно»).
- **Ноль — это число.** «Модели не было» пишется словами, а не нулём в графе стоимости.

## Эталонный адаптер

`bin/pantheon-executor` — минимальная реализация протокола поверх OpenAI-совместимого
endpoint (DeepSeek по умолчанию). Он читает задачу, кладёт в промпт объявленные пути и файлы из
них, просит один диф, вытаскивает его из ответа и печатает JSON с токенами и ценой.

Настройки — только через окружение, ключ в репозиторий не попадает:

| Переменная | Что задаёт |
|---|---|
| `PANTHEON_MODEL_KEY` или `DEEPSEEK_API_KEY` | ключ |
| `PANTHEON_MODEL_URL` | endpoint, по умолчанию `https://api.deepseek.com/chat/completions` |
| `PANTHEON_MODEL` | модель, если профиль её не назвал |
| `PANTHEON_MODEL_MAX_TOKENS` | потолок, когда коробка не вычислила комнату (прямой вызов), по умолчанию 4096 |
| `PANTHEON_MODEL_PRICE_IN`, `PANTHEON_MODEL_PRICE_OUT` | доллары за миллион токенов; без них цена неизвестна |
| `PANTHEON_MODEL_THINKING` | `disabled` — просить endpoint не тратить комнату на размышление; по умолчанию поведение провайдера; замер E показал, что глобально это не помогает |

Цены для `deepseek-flash` в этом проекте уже объявлены в примерах trajan: 0,30 $ за миллион
входных и 1,20 $ за миллион выходных (пиковые, проверено 2026-11-23,
`https://api-docs.deepseek.com/quick_start/pricing`). Те же числа подходят для переменных выше.

Включение в коробке:

```bash
cp ~/pantheon/castra/trajan/persona/executor.toml.example \
   ~/pantheon/castra/trajan/persona/executor.toml
# в файле: command = "/home/ubuntu/pantheon/bin/pantheon-executor"
PANTHEON_MODEL_KEY=… PANTHEON_MODEL=deepseek-flash \
PANTHEON_MODEL_PRICE_IN=0.30 PANTHEON_MODEL_PRICE_OUT=1.20 \
./bin/pantheon dispatch trajan --task mandata/t-2.toml
```

## Исполнитель внутри коробки

У коробки есть свой агент: `pantheon up` запускает `gateway run` в контейнере, профиль
(`persona/SOUL.md`, копируется в `cella/` при первом старте) и модель — часть коробки. Тогда
исполнителем становится `bin/pantheon-executor-container`: он переводит задачу в один промпт,
зовёт `hermes -z` внутри контейнера, забирает диф и **счёт самого агента** (`--usage-file`:
вход, выход, кэш, оценка стоимости). Проект внутри контейнера смонтирован только на чтение,
поэтому агент физически не может писать: он предлагает, а применяет Caesar на машине.

Ключ модели — секрет коробки: `cella/.env`, режим 600, вне git; `up` записывает его из
окружения вызывающего. В compose-файл ключ не попадает (и не может: `sudo` вычищает окружение).
Первый конфиг агента `up` сеет от имени владельца cella: `config.yaml`, написанный root,
переживает старт контейнера, и тогда бэкап агента падает с `Permission denied` на первом ответе.

Живой прогон на чужом проекте (`click#2847`, 2026-11-26) добавил в промпт две вещи. Сначала
проверки (тесты, типы) прогоняла только коробка после ответа, а не агент: в контейнере не было
venv проекта и pytest, и попытки запустить чужой набор сжигали комнату вызова — первый прогон был
убит на 300 с, хотя правку агент нашёл за минуту. **С 2026-11-26 (ADR-051) самопроверка разрешена:**
`up` ставит инструменты, без которых набор проекта красный по причине среды (`less`), карточка
называет рабочую команду, а агент гоняет её в своей копии проекта в `/opt/data/work/` — ворота всё
равно решают своим прогоном. Замер на двух первых задачах серии: 1,47¢ и 0,43¢ с первого ответа
против 2,58¢ (две попытки) и 0,74¢ без самопроверки. Пути в дифе — от корня проекта (`a/src/...`, `b/src/...`), даже если
агент проверял правку в своей копии: проект смонтирован только на чтение, и диф от копии ворота не
примут.

**Среда коробки: три дефекта, найденные замером.** Голый агент в том же контейнере не мог
получить зелёный набор ни при какой правке, и причин было три, все проверены по одной
(`pilot/bare-honest/`). Потолок памяти 512 МБ убивал ход по OOM через 20 с: шлюз и CLI агента
занимают ~370 МБ, ядро снимало `hermes`, и это же «Gateway disconnected» рвало вызовы в серии;
теперь `MEMORY_LIMIT = "1g"` (ADR-050). В образе нет `less`, поэтому 24 теста пагинатора красны
всегда — коробка этого не замечает, её ворота гонят набор на хосте, а замер внутри контейнера
замечает. И `.venv` в копии профиля собран на Python 3.12, а системный в контейнере 3.13:
`.venv/bin/python -m pytest` говорит «No module named pytest», работать можно через
`PYTHONPATH=src:.venv/lib/python3.12/site-packages`.

**Счёт упавшего вызова.** `--usage-file` пишется, когда ход закончился нормально; убитый или
оборванный ход не оставляет файла, и раньше такой вызов заряжался по потолку коробки — как самая
дорогая задача, а не как то, что он стоил. Теперь `bin/pantheon-executor-container` при ненулевом
коде выхода, таймауте и ответе без дифа читает счёт из того же usage-файла, а если его нет — из
собственной базы сессий агента (`cella/state.db`, таблица `session_model_usage`; берутся строки,
начатые этим вызовом). Найденная цена уходит в ответ полем `usage` с `billing_status = billed`, и
сторож считает факт, а не потолок; не нашлось ничего — по-прежнему `unknown`, а потолок остаётся
честной верхней границей.

**Карточка среды.** `persona/environment.md` — устойчивые факты о проекте (пути, команды проверок,
интерпретатор, инварианты), которые не меняются от задачи к задаче. Исполнитель читает её с хоста и
ставит в начало промпта, до задачи; в заметки записи уходят первые 12 символов её хеша
(`environment card <hash>`), чтобы было видно, с какой карточкой шёл прогон. Смысл двойной: агент не
добывает одно и то же заново (в замере с голым агентом это стоило 83 секунды), а общий блок промпта
одинаков у всех задач коробки и может оставаться в кэше провайдера. Карточка — память о среде, а не
о задаче: история правок живёт в архиве и приходит отдельным блоком ниже. Карточка доходит и до
архитектора (`role = "architect"`): карта проекта — слои, точки входа, инварианты — живёт в ней же,
чтобы анализ начинался не с чтения дерева, а с уже названных фактов.

**Пакет контекста.** Перед задачей исполнитель получает блок, собранный кодом, а не поиском:
рамка, на которой стоит задача, и **одна строка последствия** — сколько записанных изменений
касается этих путей, какое из них последнее (задача, вердикт, тема) и что отмена записанного
решения — дело владельца. Всё это ограничено 600 символами: длинная тема режется по слову, а не
тащится целиком. Адреса, причины и весь отбор — какие записи совпали, какие не влезли — остаются
в JSON пакета, где их читает человек; в промпт они не идут.

Почему строка, а не список. До 2026-11-26 блок печатал до шести строк записей с адресом и путём
файла каждой. Замер (`pilot/context-block/`) показал: за шесть боевых прогонов ни один не открыл
ни одной записи, а на задаче, отменяющей записанное решение, ответ с этим списком и без блока
совпал побайтно. Список был указателем в пустоту: модель читает git, а в сообщении коммита уже
лежат номер задачи, вердикт и тема (`subject`). Поэтому блок теперь называет решение, а не
перечисляет файлы, и стоит около 110 токенов вместо 640. Второй заход на той же задаче: строка
прочитана и названа в рассуждении («Context history: t-… (pass)»), правка та же, что без блока, а
цена хода с 110 токенами отличается от цены без блока в пределах разброса модели. Уникальная
ценность строки — история, которой нет в git: остановленные и возвращённые попытки.

## Границы, названные явно

- **Порт под агента не публикуется**: gateway слушает петлевой адрес внутри контейнера, наружу
  выставлен только `docker exec`/`docker compose exec` — этого хватает исполнителю, но не
  браузеру. Публичный доступ к агенту — отдельное решение.
- **Проверка «не писал сам» — по git.** Проект не под git — предупреждение в записи, а не тихая
  уверенность.
- **Один диф за вызов.** Нет потокового вывода и нет инструментов: команда читает проект и
  отвечает, а коробка решает, спросить ли ещё раз (`steps`) или жить с ответом (`one-shot`).
  Произвольные команды модели не разрешаются: песочницы, которая удержала бы запись мимо ворот, у
  нас нет.
- **Команда доверенная в одном смысле:** ей можно читать проект. Писать — нельзя, и это
  проверяется, а не обещается.
- **CLI под подписку** (`claude -p`, `codex exec`) — отдельный адаптер того же протокола; тогда
  бюджет считается попытками и минутами, а в записи честно стоит «модель не наша, лимиты
  вендора». Решено после MVP, этап 3 дорожной карты.

## Проверка проверки: `pantheon preflight`

Задача ремонта настоящая, когда её `repro` падает на базе. `pantheon preflight <box> --task
<файл> [--fix <ref>] [--json]` проверяет это до оплаты модели: гоняет ту же команду на рабочем
дереве (обязана упасть) и, если назван `--fix`, в отдельном worktree этого коммита (обязана
пройти). Ничего не пишет: ни записи, ни контракта, ни события — ошибка критерия не должна стоить
денег и оставлять след, который потом читается как работа.

- Базовое дерево — рабочее, а не коммит: это дерево, о котором спросят модель.
- `--fix` — коммит, который считается правильным исправлением (обычно фикс из трекера). Проверка
  «падает до, проходит после» отсекает критерий, который описывает не тот дефект или не может быть
  удовлетворён.
- Worktree — это коммит, а не рабочее дерево: неотслеживаемых файлов в нём нет. Виртуальное
  окружение проекта подключается симлинком, чтобы проверка шла проектным интерпретатором.
- Отказы: нет `repro` или неизвестный `--fix` — ошибка вызова (код 2); проверка зелёная на базе
  или не проходит на фиксе — отказ (код 1) с причиной. Код 0 — критерий живой.
- Preflight не заменяет `dispatch`: он проверяет критерий, а не задачу, и ничего не записывает.

## Аудит мутаций: `pantheon mutate`

Проверка может быть зелёной и при этом не видеть того, что должна защищать. `pantheon mutate <box>
--file <аудит> [--json]` отвечает на этот вопрос до того, как на него ответит утёкший баг: поломка
названа человеком, применяется к копии дерева, и проверка либо краснеет, либо расписывается в
слепоте. Модель не вызывается, деньги не тратятся.

- Объявление — файл: `check` (argv проверки), необязательные `task` и `why`, и `[[break]]` с
  `path`, `old`, `new`, `why`. Неизвестный ключ — ошибка: объявление, которое никто не прочитает,
  мусор.
- Дерево — то же, что судил бы `dispatch`: HEAD, рабочий диф и неотслеживаемые файлы, не попавшие
  в ignore, в одноразовом worktree; venv проекта подключён симлинком. Базовая проверка сначала
  обязана быть зелёной, иначе аудит отказывается: красная проверка не может ничего заметить.
- Каждая поломка — своя копия дерева. Ответ: `noticed`, `blind`, `not-applied` (строки нет в
  дереве), `invalid` (поломка не компилируется — покраснение было бы ложью), `timeout`.
- Кэши bytecode и инструментов в копии стираются: иначе поломка того же размера в ту же секунду
  mtime оставляет старый `.pyc`, и проверка «проходит» на сломанном коде.
- Это аудит, а не гейт (ADR-048): выжившая поломка не возвращает задачу, вердикт не меняет и не
  гоняется на каждой правке. Каждый прогон пишет запись в `tabularium/mutatio/` — адрес поломки,
  исход и причина; записей задач это не касается.
- Потолки: до 10 поломок и 300 с на чтение; что не влезло, называется числом, а не теряется.
