# 03. Integration Architecture

## Принцип

Компоненты не вызывают друг друга как библиотеки. Взаимодействие — три соглашения:
**файлы** (данные проекта и записи работы), **команда** (argv → json + код возврата), **идентификатор**
(всё, на что можно сослаться, имеет стабильный id). Это даёт запуск из коробки, из CI, из редактора и с
другой машины без переписывания.

## Поверхность команд (минимум)

| Команда | Что делает | Кто зовёт |
|---|---|---|
| `pantheon new <путь>` | создаёт коробку, пишет `box.toml`, compose, профиль | человек |
| `pantheon up` / `down` | поднимает и гасит контейнер Августа | человек |
| `pantheon status [box]` | состояние из записей: рамка, записи, задачи, пробелы новейшей задачи | человек |
| `pantheon dispatch --task <файл>` | задача через контуры: архитектура, ворота, проверки, коммит, сводка в outbox | Август, человек |
| `pantheon step --campaign <id> --step <id>` | шаг плана тем же путём, с записью в состояние кампании; `--retry` — ещё попытка по правилу повтора | Август, человек |
| `pantheon advance --campaign <id>` | ведёт auto-кампанию по её правилу: готовый шаг, повтор по решению кода, остановка с причиной; `manual` и грязное дерево — отказ | Август, человек |
| `pantheon resume <box> --task <id>` | продолжает прерванную задачу с её артефактов; модель зовётся только на повтор | человек |
| `pantheon run --contract <файл> --patch <файл>` | Caesar: проверка контракта, попытка, артефакты, событие | Август, человек |
| `pantheon verify [box]` | Trajan: план проверок, прогон, вердикт, артефакты; `--review` читает агент коробки | Август, человек, CI |
| `pantheon arch [box]` | Aurelius: модель против кода, нарушения | Август, человек |
| `pantheon approve [box]` | принимает рамку проекта записью с отпечатком | человек |
| `pantheon campaign [box]` | вердикт по планам кампаний, считанный кодом | человек, Август |
| `pantheon records [box]` | пересобирает и печатает дайджест записей | человек, Август |

Все команды печатают json при `--json`, код возврата означает результат, а не настроение: 0 — сделано,
1 — отказ по правилу, 2 — ошибка исполнения или остановка прогона с названной причиной (`advance`).

## Поток сквозного сценария

1. Человек ставит задачу текстом. Август пишет `tasks/<id>.toml`: цель, объявленный объём (пути, тип:
   docs/bugfix/feature/architecture/security), критерий готовности, бюджет.
2. Август по таблице (объём → контуры) решает, нужен ли Aurelius, и зовёт `pantheon arch check` или
   получает выдержку ограничений из модели.
3. Август зовёт `pantheon run`: Caesar валидирует контракт (пути, инструменты, лимиты, разрешения),
   запускает исполнителя, пишет попытку и артефакты.
4. Август зовёт `pantheon verify`: Trajan строит план по путям и политике, гоняет проверки, вызывает
   ревью, считает вердикт кодом, пишет отчёт и событие.
5. Август читает вердикт и обновляет проекцию: задача закрыта или возвращена с находками; при `HOLD`
   повторная попытка — только с новой записью и новым бюджетом.
6. `pantheon outbox flush` пишет сводку для личного Hermes.

Шаги 2–4 — разные команды, поэтому любой из них можно запустить вручную: это и есть проверка
независимости компонентов.

## Продолжение прерванной задачи

Задача может остановиться на середине: исполнителя убили, машина перезагрузилась, кончился бюджет.
`pantheon dispatch` кладёт рядом с артефактами снимок задачи (`artifacts/<id>/task.json`) и копию
объявленного патча, поэтому продолжение не требует ни исходного файла задачи, ни памяти о том, что
происходило. `pantheon resume <коробка> --task <id>` читает снимок и артефакты и продолжает с того места,
где остановилось:

| Что осталось на диске | Что делает `resume` |
|---|---|
| ворота применили изменение, записи о проверке нет | проверяет то дерево, которое изменили ворота |
| предложение записано, ворот не было | проводит записанный патч через ворота и проверку |
| вызов стоил дороже бюджета | отказывается применять, пока лимит не поднят: `--max-cents` берёт уже оплаченный вызов, а не платит второй раз |
| исполнитель не ответил | без `--retry` отказывается: продолжать нечем, поэтому сначала новый вызов |

Чего `resume` не делает: не просит модель заново о том изменении, которое уже лежит на диске; не
проверяет дерево, в котором применённого изменения уже нет (и не закрывает такую задачу); не
пересчитывает вердикт, который уже посчитан — закрытая задача продолжению не подлежит. Событие
`task.resumed` и строка `resumed from` в записи и в outbox говорят, откуда продолжили.

## Повтор проверок

Проверка на неизменившемся дереве не гоняется второй раз. Перед прогоном коробка считает
отпечаток: содержимое рабочего дерева проекта (коммит, диф к нему и содержимое неотслеживаемых
файлов), файл политики и исходники самого Траяна. Рядом с каждым прогоном она пишет
`box-verify.json` — на чём вердикт держался и какой отчёт он собой закрыл.

Дерево считается по путям от корня репозитория, а не от каталога, где запущена команда: проект
может жить в подкаталоге, и его файлы всё равно входят в отпечаток. Это не теория — на демо-коробке
проект лежит в `trajan/`, и без `--full-name` у `git ls-files` отпечаток видел набор путей с
«absent» вместо содержимого, поэтому правка модели оставляла его прежним и вердикт про старое дерево
переиспользовался для нового. Тест `tests/test_reuse.py::test_a_project_inside_a_repository_digests_its_own_content`
держит это.

Если отпечаток совпал с прошлым прогоном, `verify` не запускает проверки: ответ берётся из того
отчёта, а новая запись и вывод команды говорят `reused` и откуда именно. Что переиспользуется и
что нет:

| Случай | Что происходит |
|---|---|
| `pass` или `pass_with_conditions`, дерево и политика те же | повтор: тот же отчёт, новая запись со ссылкой на старую |
| `hold` | прогон заново: если человек смотрит снова, он обычно что-то починил |
| `inconclusive` | прогон заново: вердикт не решён, а причина могла быть в среде |
| изменилось дерево, файл политики или исходники Траяна | прогон заново |
| прошлому прогону больше суток | прогон заново: время не входит в отпечаток |

Что отпечаток не покрывает и что поэтому сказано вслух: файлы под `.gitignore` (проверка,
читающая их, может ответить иначе на том же отпечатке), версии интерпретатора и установленных
инструментов. Отсюда окно в сутки и обязательная строка `reused from` в записи, outbox и выводе
`verify`: повтор — это утверждение «входы те же», а не «проверки прошли ещё раз».

## Кто читает изменение

Проверки не видят смысла: они зелёные и на делении на ноль. Поэтому изменение читает тот же агент
коробки, что его и писал, — но с другой стороны контура: ему дают диф, просят находки с точной цитатой
строки, и дальше решает репозиторий, а не модель.

Кто читает, решает коробка — так же, как она решает, кто пишет: файл `profile/reviewer.toml`
объявляет `enabled`, модель и потолок в центах. Файла нет — коробка по умолчанию ничего не читает,
и `new` кладёт рядом пример, который надо включить одной строкой; `status` показывает, что
происходит сейчас. Флаги перебивают файл: `--review` читает один раз и на коробке, которая
ничего не объявляла, `--no-review` отказывается на один прогон, не трогая файл.
`--reviewer MODULE:FACTORY` остаётся для своего читателя, например
`trajan.review.factory:from_env` с прямым API-ключом.

Потолок чтения — не то же, что бюджет исполнителя: вызов уже состоялся, поэтому чтение дороже
объявленного не отменяется, а записывается и называется пробелом. Так «закрыто» не может
сделаться тише от того, что цена оказалась выше ожидаемой.

Связь между Траяном и коробкой — команда, а не импорт: `trajan.llm.command:from_env` кладёт запрос
JSON в stdin `bin/pantheon-review`, а тот говорит с контейнером через `docker compose exec` — тот же
путь, что у исполнителя. Проект внутри смонтирован только на чтение, так что читатель не может
«поправить» то, что судит. Каждая находка проверяется якорем: файл из дифа, строка в нём есть, цитата —
буквально эта строка; иначе находка остаётся `unverified`, видна в отчёте и вердикта не двигает.

Счёт читателя лежит рядом с прогоном (`review-usage.jsonl`, строка на вызов) и попадает в запись,
outbox и `status`; если агент не сообщил цену, там стоит «не сообщил», а не ноль. А вот ответ,
который Траян отдал из своего кэша ревью, записан с `cached: true`: вызова не было, и счёт за него
не спрашивают — иначе коробка обвиняла бы читателя в сокрытии счёта, которого тот не выставлял.

**Читается то, что применили — исправлено 2026-11-24.** Диф исполнителя живёт в попытке
(`artifacts/<task>/<n>/change.diff`), а не в файле задачи, и до этой правки `dispatch` считал, что
изменения нет: прогон, только что применивший диф, писал «читать нечего», и включённый читатель
молчал. Теперь читателю передаётся диф из попытки — тот самый, что применили ворота, — и запись не
может сказать «не читали», когда читать было что.

Живой прогон 2026-11-24 на коробке `trajan-mvp`: малое изменение, которого не видят ни тесты, ни
линт, — 3 находки, все подтверждены якорем (деление на ноль и два замечания), вердикт
`pass_with_conditions`, 11 107+1 029 токенов, 0,08 цента. Второй прогон — `dispatch --review` по
задаче `t-docs`: `pass`, `closed`, «read by deepseek-flash», 0,02 цента, и в разделе «чего не
проверили» осталась одна строка `none`.

## План проверок по изменению

Проверка в политике может объявить `when_paths` — пути, которые она охраняет. Когда контур
получает само изменение (а получает он его только с читателем: «изменение без читателя» Траян
отказывается смотреть), план выбирает проверку, только если хоть один изменённый путь попадает под
её шаблоны. Непопадание — это **not selected**: решение, а не пробел, и отчёт печатает его
отдельной таблицей с причиной, а строка коробки — списком `not selected: tests, types`.

В политике самого `trajan` так объявлены `tests` и `types`: правка в `docs/` не может их
сломать, и минута ожидания ради этого не нужна. `lint` и порог тестов (`test-floor`) остаются на
каждом изменении: линт дёшев, а порог — та проверка, которая заметит зелёный прогон, полученный
удалением тестов.

## Повтор проверок и повтора ответа

Отпечаток, по которому переиспользуется вердикт, включает теперь и само изменение, и факт чтения:
дерево, политика, исходники Траяна, содержимое дифа и «читали или нет». Поэтому:

- вердикт про диф не подменяется вердиктом про то же дерево без дифа — это разные вопросы;
- прочитанный вердикт не выдаётся за нечитанный и наоборот;
- повторный `dispatch` той же задачи отвечает за 0,2 с, не зовя ни модель, ни проверки, а
  стоимость прочтения переезжает в новую запись из старой — иначе повтор выглядел бы дешевле,
  чем прогон, который за него заплатил.

Собственные записи Траяна внутри проекта (`.trajan/runs/`, `.trajan/cache/`) в отпечаток не
входят: их пишет сам контур во время прогона, иначе отпечаток менялся бы ровно тем прогоном,
который только что судил дерево. Кэш ревью при этом остаётся: если тот же диф уже читали, второй
прогон берёт ответ из кэша, и коробка так и говорит — «served from the review cache, this run paid
nothing», а не «не сообщил цену».

## Чего прогон не проверил

Слово «closed» в записи отвечает только за то, что было посчитано. Поэтому каждая запись, outbox
и `status` называют пробелы явно, разделом «what we did not check»:

- вердикт получен прогоном **только проверок** (без `--review`) — изменение никто не читал, и про
  его смысл вердикт ничего не говорит;
- читателя **позвали, и он не ответил** — это не то же самое, что его не звали;
- читатель **не сообщил расход** — чтение было, а счёта за него нет;
- вердикт **переиспользован**: проверки сейчас не гонялись, это ответ про то же дерево, посчитанный
  раньше;
- архитектура **не подтверждена** (`unchecked`), потому что нет модели или нет инструмента;
- проверка **не маршрутизирована** или не оставила результата;
- исполнитель **не сообщил расход** — бюджет проверить нечем;
- задача **не объявила бюджет** — прогон ничем не ограничен.

Пустой список печатается как `- none`: «ничего не осталось» — это утверждение, которое тоже надо
увидеть, а не догадаться о нём по отсутствию строки.

## Ворота, git и утверждение рамки

**Ворота уже проверяют вид, а не только контракт.** Вид задачи ограничивает пути: без файла
`.pantheon/kinds.toml` действует встроенная политика — архитектура владеет `.pantheon/**`, `docs/**`
и `.trajan/context.toml`, а остальные виды в рамку не пишут. Проект может объявить свою таблицу;
сломанная таблица останавливает ворота, а не игнорируется. Отказ пишется в попытку как
`outside-kind` или `kind-forbidden`.

**Коммит после вердикта — сделан 2026-11-24.** Зелёный вердикт (`pass`) делает изменение коммитом:
Цезарь собирает коммит из `HEAD` плюс записанное изменение во временном индексе, поэтому правки,
которые лежали в дереве до ворот, в коммит не попадают и остаются правками — вердикт был про
изменение, и коммит тоже про него. В сообщении: задача, вердикт, путь к отчёту, отпечаток изменения;
автор служебный `Pantheon <pantheon@harness.invalid>`; пуш — только по просьбе владельца.
Вердикт не зелёный — изменение остаётся черновиком в дереве, коммита нет. Дерево ушло, изменение уже
в `HEAD`, git отказал — это `skipped` или `failed` с причиной в `commit.json` и в event ledger, а не
тишина; в записи отправки и в outbox тогда появляется строка «изменение в дереве, но не в git».
`--no-commit` оставляет дерево и тоже пишет причину. Режим кампании — поле `mode` задачи: `manual` —
обычный, `auto` объявлен и отказывает, пока нет исполнителя кампании (ADR-018).

**Утверждение рамки — сделано 2026-11-24.** Рамка — названный список файлов:
`.pantheon/architecture.toml` (модель), `.pantheon/kinds.toml` (политика путей),
`.trajan/context.toml` (требования). Список явный, а не `**`: бриф или план, положенный в
`.pantheon/` позже, не должен молча стать частью того, что владелец принял. `pantheon approve`
пишет в коробку запись `artifacts/frame/approval-<время>.json`: отпечаток каждого файла, общий
отпечаток, кто принял, зачем и на каком коммите. Запись не перезаписывается — второе принятие
это вторая запись, чтобы история принятого оставалась читаемой. Отсутствующий файл перечисляется
как отсутствующий, а утвердить пустую рамку нельзя: «одобрено ничего» выглядело бы как снятый
вопрос. Каждая отправка читает рамку и сравнивает с новой записью — `approved`, `changed`,
`never` или `empty`; всё, кроме `approved`, попадает в «что мы не проверили» и в сводку, а
`status` печатает строку `frame`. Задача может закрыться против неутверждённой рамки, но не
может закрыться тихо: пробел назван в записи, и его видно.

## Кампания и план

**Объект кампании и вердикт кодом — сделано 2026-11-24.** План — файл в репозитории
`.pantheon/campaigns/<id>.toml`: замысел, рамка, против которой он написан, шаги, приёмка и бюджет.
Шаг объявляет id, цель, вид, роль, пути, ожидаемый результат, зависимости и потолок в центах.
Приёмка — список пунктов, и каждый пункт обязан называть шаг: покрытие свободного текста — это
вердикт шага, а не чужое мнение.

Проверка до старта находит сразу всё: повтор id, зависимость на несуществующий шаг, петлю
(`s1 → s2 → s1`), путь вне того, что владеет вид, архитектурный шаг с ролью исполнителя и наоборот,
пункт приёмки на несуществующий шаг, неположительный бюджет. Неизвестное поле — ошибка, а не
пожелание.

Состояние — в коробке, `artifacts/campaign/<id>/state.json`: какие шаги закрыты, с каким вердиктом,
сколько стоили. Запись чужой кампании в свой файл состояния — ошибка: одна запись не может врать о
двух планах. Вердикт считает код: `ready` (ничего не шло), `in progress`, `incomplete` (все шаги
записаны, но что-то не выполнено), `complete` (каждый шаг со строгим `pass`, приёмка держится на них,
рамка утверждена, бюджет не превышен) или `over budget`. `pantheon campaign` печатает это по каждой
кампании проекта, `--file` — по одной.

**Запуск шага — сделано 2026-11-24.** `pantheon step --campaign <id> --step <id>` собирает из шага
задачу и проводит её тем же путём, что и `dispatch`: исполнитель, ворота, проверки, чтение, коммит.
Шаг — это работа, поэтому маршрут дополняется стадией `run`: иначе документный шаг закрывал бы чистую
проверку нетронутого дерева. Закрытым шаг считается только если изменение действительно появилось;
прогон, который ничего не написал, записывается как `noop`, кампания его не считает, а команда
выходит с кодом 1. Зависимости проверяются до запуска: шаг ждёт, пока зависимые не закроются строгим
`pass`. Если файл плана изменился после прошлого шага, запуск отказывает и требует `--reason` — так
механическая правка (разбить, сузить, переставить) записывается ревизией с причиной, а смысловая
правка без причины просто не проходит. Вердикт и стоимость шага пишутся в состояние кампании и в
ledger, и повторный `pantheon campaign` показывает новый вердикт.

## Дайджест записей и пакет контекста

**Память проекта пишет код — сделано 2026-11-24.** У каждой законченной задачи в коробке остаётся
запись: контракт, попытка ворот, отчёт проверки, коммит. Читать их все, чтобы ответить «что здесь уже
происходило вокруг этих путей», дороже самой работы, поэтому код пишет дешёвый ответ —
`artifacts/records/digest.json`: одна строка на задачу (цель, вид, вердикт, тронутые пути, адрес
полной записи). Дайджест детерминирован (те же записи — тот же отпечаток; время сборки в хеш не
входит), ограничен (записи, пути и длина цели обрезаны) и честен на краях: не влезшее считается,
нечитаемая запись называется с причиной, а не пропадает. `pantheon records` пересобирает его и
печатает, `pantheon status` говорит `fresh` / `stale` / `not written yet`. Дайджест пишется после
записи задачи: иначе каждый прогон оставлял бы за собой устаревший индекс.

**Пакет контекста — сделано 2026-11-24.** Перед тем как спросить модель, код собирает
`artifacts/<task>/pack-<at>.json`: утверждённая рамка с отпечатком, прошлые задачи, чьи тронутые
пути попадают в объявленный объём (с причиной «touches docs/design.md»), и указатель на полную запись
каждой. Модель получает пакет — несколько сотен символов, потолок 4000; полные записи она открывает,
только если это решает работу. Отбор ограничен шестью записями; всё, что не вошло (другая область,
потолок отбора, потолок размера, собственный прошлый прогон, нечитаемая запись), названо в самом
пакете строкой `left out`. Пакет уходит в `request.json` исполнителя, в `dispatch-*.json`, в outbox и
печатается при `dispatch --json`: по записи видно, что модель знала до первого токена. Журнал
прочитанного и бюджет токенов на задачу — следующий шаг, не выдуманный сейчас.

**Режим, потолок попыток и правило повтора — сделано 2026-11-24.** Кампания объявляет `mode`
(`manual` / `auto`) и `attempts` — сколько попыток разрешено одному шагу. `auto` исполняет раннер — `pantheon advance`
(см. ниже), а `manual` раннером не запускается. Повтор — не перезапуск по настроению:
`pantheon step --retry` спрашивает решение у кода. Стоп сразу, если записана остановка, если попытки
исчерпаны (`2 of 2`), если бюджет кампании потрачен, если вердикта нет вовсе (ворота отказали) или
если находка указывает вне объявленных путей — тогда меняется план или рамка, а не попытка. Повтор
разрешён, когда у причины вердикта есть место внутри путей (`location.file` находки) или её назвала
проверка: она судит объявленное изменение. Перед повтором черновик провалившейся попытки
откатывается её же диффом (`git apply --reverse`, событие `step.draft-reverted`), чтобы повтор
начинался от принятого дерева, а коммит оставался «HEAD + изменение»; если дерево ушло и откат
невозможен, повтора нет. Модель, ответившая тем же диффом, второй раз не применяется: отпечаток
сверяется в координатах проекта, и шаг записывает остановку «the change did not change».
`pantheon campaign` показывает `mode`, `attempt N of M` и по каждому не закрытому шагу —
`next: retry` или `next: stop` с причиной.

## Автономный прогон кампании

**Раннер исполняет план — сделано 2026-11-24.** `pantheon advance --campaign <id>` берёт первый по
плану шаг, чьи зависимости закрыты, и проводит его той же дорогой, что `pantheon step`: тот же шаг,
те же ворота, проверки, чтение и коммит. Второго пути исполнения нет — и `step`, и `advance` зовут
одну функцию в `harness/runner.py`, поэтому ручной шаг и прогон не могут разойтись в поведении.
После шага раннер спрашивает у кода, разрешена ли ещё попытка (D20): разрешена — шаг повторяется,
отказано — прогон останавливается и называет причину. Останавливают прогон: записанная остановка,
исчерпанные попытки, потраченный бюджет, шаг, который ничего не написал (`noop`), отказ ворот без
вердикта, отсутствие готового шага, закрытые шаги при невыполненной приёмке или неутверждённой рамке.
Число итераций — не константа: это сумма попыток по шагам плана (`len(steps) * attempts`), то есть
ровно то, что владелец объявил; исчерпав его, прогон тоже останавливается и говорит, что осталось.
Перед стартом прогон смотрит на дерево проекта: если в нём есть незакоммиченные правки, `advance`
не начинает работу и перечисляет пути. Проверки судят дерево целиком, поэтому прогон поверх чужого
черновика дал бы вердикт не про своё изменение; ручной `step` при этом остаётся доступен — это
осознанный выбор человека, а не автоматический.

Каждый прогон пишет свою запись `artifacts/campaign/<id>/run-<время>.json` (шаги по порядку, что
закрылось, стоимость, причина остановки, вердикт) и одну строку в ledger — `campaign.completed` или
`campaign.stopped`. Код возврата: 0 — кампания `complete`, 2 — прогон остановился (причина уже
напечатана). `--json` добавляет к вердикту кампании объект `run`. Одиночная задача с `mode = "auto"`
по-прежнему отказывает: автономность принадлежит кампании, которую кто-то ведёт, а один `dispatch`
никто не повторит — и это сказано в отказе, а не замолчано.

## Как ограничен Август

Профиль коробки (ACL Hermes) выдаёт ему:
- чтение проекта и файлов коробки;
- `pantheon` CLI как инструмент;
- запись **только** через CLI-команды, которые сами пишут реестр;
- отсутствие родного shell, редактора и произвольной записи файлов.

Проверка этого — тест: попытка Августа записать файл вне контракта должна быть отклонена окружением, а не
уговариванием. Если ограничение держится только инструкцией в `SOUL.md`, оно не существует.

## Форматы

- Задача и контракт — TOML: читаются человеком, диффятся, не требуют библиотеки.
- Артефакты прогона — каталог с `report.json` и `report.md` (формат trajan): вердикт машинно читаемый,
  человеку — рендер.
- Реестр — `ledger/<дата>.jsonl`: одна строка — одно событие со ссылками на артефакты. Дописывается,
  не переписывается.
- Схемы данных версионируются (`schema_version`), и компонент обязан отказаться читать чужую версию,
  а не угадывать.

## Деградация

| Что отсутствует | Что всё ещё работает |
|---|---|
| Август (контейнер не поднят) | `pantheon verify`, `arch check`, `status` по реестру — вручную |
| Aurelius (нет модели) | Trajan проверяет по политике; архитектурная проверка помечается «не выполнялась» |
| Caesar (нет контракта) | `verify` работает по изменению в рабочем дереве; запись попытки помечается ручной |
| Trajan (нет политики) | `run` исполняет, но результат помечается «не проверено», вердикта нет |
| личный Hermes | ничего не меняется: коробка от него не зависит |

Правило: отсутствие компонента — это видимое состояние (`not_applicable`, «не выполнялось»), а не тихий
пропуск.

## Связь с личным Hermes

Только `outbox/`: одна сводка на закрытую задачу — что сделано, какой вердикт, какие решения приняты,
что осталось. Личный Hermes читает и накапливает свой контекст. Обратный поток отсутствует: коробка не
запрашивает у ассистента память и не зависит от его доступности. Позже можно добавить сводку по всем
коробкам, но это задача ассистента, а не Пантеона.
