# Reports

Every report here answers a different question. The evaluation reports (live and stub) say what a
model does on a dataset; `verification_demo/` and `review_self/` are verification reports and say
what the checks and the reviewer found in a change. Open a live one if you want to know what a
model does; open a stub one if you want to see the loop without a bill.

## Live run: `deepseek-flash` / `deepseek-v4-pro`, 2026-11-22

[`baseline.*`](baseline.md), [`guarded.*`](guarded.md) and [`diff.md`](diff.md) come from a real run:
32 cases, `deepseek-flash` as the agent, `deepseek-v4-pro` as the judge, `QAGENT_RECORD=1` so every
answer is in `examples/logistics_intake/cassettes/deepseek-flash.jsonl` (71 requests, 72 KB).
Reasoning was switched off at the provider (`reasoning_effort: none`, decision U37) — otherwise the
hidden thinking cost about ten times the run.

| | baseline | guarded |
|---|---|---|
| Pass, final | 59.4% | **81.2%** |
| Pass, first attempt | 59.4% | 68.8% |
| False pass rate | 40.6% | **18.8%** |
| Retry recovery | — | 66.7% (6 of 9) |
| Escalation rate | 0.0% | 0.0% |
| Field accuracy (macro) | 96.2% | 98.1% |
| Cost, total | $0.0266 | $0.1076 |
| Cost per passed case | $0.0014 | $0.0041 |
| Latency p50 / p95 | 1.4 s / 1.9 s | 3.0 s / 6.2 s |

Reproduce the guarded column for free — no key, no network:

```bash
make replay    # QAGENT_LLM=replay: same 81.2%, latency drops to milliseconds
```

What the table means:

- **False passes are the point.** In `baseline` mode 13 of 32 answers are accepted and are wrong
  against the golden values; in `guarded` mode 6 are, and [`diff.md`](diff.md) names every case
  that changed.
- **The gate is not free.** Six answers were returned for repair — first-attempt pass 68.8% against
  81.2% final — and four of the six came back correct. Two stayed wrong and are among the six false
  passes, which is what `retry_recovery` is for.
- **The two columns are two samples, not the same answers.** The endpoint is not bit-deterministic
  even at `temperature=0`, so guarded's first attempt (68.8%) is not the baseline number (59.4%)
  plus a gate; compare final numbers and per-case rows, not single percentages.
- **Nothing escalated.** The judge disagreed with the gate often enough that every case either
  passed or was fixed by one retry. That is a result, not a missing feature: the escalation path is
  exercised in the stub reports below and in the unit tests.
- **What still slips through** is mostly `request_type` (quote vs. booking is a judgement call on
  the edge cases) and two adversarial traps where only the golden data knows the email never said
  it: `adv-01` invents a pickup date, `adv-03` derives country codes from city names.

## Stub run: demo agent, no model calls

[`sample_baseline.*`](sample_baseline.md), [`sample_guarded.*`](sample_guarded.md) and
[`sample_diff.md`](sample_diff.md) are generated by `make sample` from
[`examples/logistics_intake/demo.py`](../examples/logistics_intake/demo.py).

**These are stub runs: no model was called.** The demo agent replays each golden answer with one
scripted defect, so the reports show how the loop, the checks and the metrics behave — not how a
model performs. Every file starts with that label, and the agent is recorded as `demo-stub` rather
than under a real model name, so a reader who opens one file cannot mistake it for a measurement.

What the pair is meant to show:

| | baseline | guarded |
|---|---|---|
| Pass, final | 75.0% | 93.8% |
| False pass rate | 25.0% | 3.1% |
| Retry recovery | — | 88.9% |
| Escalation rate | 0.0% | 6.2% |

- **False passes** are the point: 8 of 32 answers were accepted in `baseline` mode and are wrong
  against the golden values. The gate flags 7 of them: 6 are fixed by one retry and `ed-04` never
  converges and escalates. The eighth is `adv-01`.
- **Two escalations** show the escalation path that the live run never needed: `ed-04`
  (`no_progress`) and `adv-05` (critical refusal).
- **Costs are $0.0000** because the stub reports no tokens.

Regenerate with `make sample` (deterministic, no key needed). The generated files are committed so
the README can link to them; replace them only with another stub run, and use `make eval` +
`make baseline` + `make diff` for real numbers.

## Code review example: `code_review/`

The second example has its own folder, because its numbers answer a different question: not "did
the extraction match the email" but "did the review find the planted bug and invent nothing".

### Live run: 24 cases, 2026-11-23

[`code_review/guarded.*`](code_review/guarded.md) is a real run of `deepseek-flash` with
`deepseek-v4-pro` as the judge; every answer is in
`examples/code_review/cassettes/deepseek-flash.jsonl` (48 requests). Reasoning was off at the
provider, as in the logistics run (U37).

[`code_review/baseline.*`](code_review/baseline.md) was produced by replaying the same committed
answers in `baseline` mode: identical requests, no second bill, and the comparison shows the loop
against itself rather than two samples of the endpoint.

| | baseline | guarded |
|---|---|---|
| Pass, final | 87.5% | 87.5% |
| False pass rate | 12.5% | **0.0%** |
| Escalation rate | 0.0% | 20.8% (5 of 24) |
| Retry recovery | — | 100% (1 of 1) |
| Cost, total | $0.0068 | $0.0477 |
| Cost per passed case | $0.0003 | $0.0023 |
| Latency p50 / p95 | — / — | 2.9 s / 4.7 s |

The interesting column is the middle one. Three "looks fine" answers on buggy code would have
shipped in `baseline` mode, and one invented defect on clean code would have gone out as a false
alarm; the judge escalated all four (`critical_issue`). One more pointed at the right line with the
wrong quote, which the free anchor check caught (`C3_QUOTE_NOT_ON_LINE`), and it escalated when the
retry did not fix it (`no_progress`). The pass rate did not move — correctness did not improve — but
no wrong answer was accepted.

### Stub run: demo agent, no model calls

[`code_review/sample_*`](code_review/sample_guarded.md) is generated by `make sample` from
[`examples/code_review/demo.py`](../examples/code_review/demo.py) and carries the same banner: the
agent model is recorded as `demo-stub`. It walks three loop paths on purpose — an invented quote
(caught, fixed on retry), an off-line quote (caught, fixed) and a silent "ok" that nothing
deterministic can see (the false pass of that report).

## Verification reports

Three reports come from the verification contour rather than from a dataset run. Their shape is
different on purpose: verdict first, reasons, every check with its evidence, findings, the limits
the checks ran under (and what those limits do not isolate), and the list of what was **not**
checked.

- [`verification_demo/`](verification_demo/report.md) — a project with a planted defect and a
  failing test. Verdict `HOLD`, one blocking finding, the failing assertion kept as an artifact.
  Generated by `make verify-demo`; no model involved.
- [`verification_demo_plan/`](verification_demo_plan/report.md) — the same project reviewed as a
  change that touches only `app.py`: the SQL gate is **not selected**, the `## Plan` section says
  why, and the verdict stays `HOLD` because the planted defect is still there. Generated by
  `make plan-demo` with a scripted reviewer, so it costs nothing.
- [`review_self/`](review_self/report.md) — the independent reviewer reading the diff of its own
  commit. Verdict `PASS WITH CONDITIONS`, four proposals, all four quotes confirmed by the anchor,
  and three of the four turned out to be real problems in the code that had just been written.
  Read [`review_self/README.md`](review_self/README.md) for the outcome of each finding.

## Holdout bench

[`holdout/bench.md`](holdout/bench.md) is the contour graded on a suite whose answers were
written down before the run: three planted defects (arithmetic, annotation, migration) that must
be held, and two clean changes that must not. Result: **3 of 3 held, 0 of 2 false alarms**, in a
few seconds and without a model call. Produced by `make bench`; the suite lives in
[`examples/holdout/`](../examples/holdout/README.md).
